# 34: Small decisions left from the architecture review

**What to build:** Settle a few small behaviors that need a decision before they can be built.

Spec: [Downlight v1](../spec.md)

**Blocked by:** none

**Status:** ready-for-human

- [x] **Files that aren't Markdown from the command line.** `downlight notes.txt` or `downlight some.png` renders the file as Markdown today (the spec's Open with for other formats is "later"). Decide: show it as Markdown anyway, show it as plain text, or say Downlight opens Markdown files, as a drop does. **Decided:** a file that is text renders as Markdown, whatever its extension (an extension-less README too); a binary file is refused with a notice that says Downlight opens text files. The same rule holds however the file arrives: the command line, a drop and Open (whose dialog still filters to Markdown by default, with an "All files" choice). How a file is told to be binary is the implementer's, in the core, and the spec and glossary say the new rule.
- [x] **Drive-relative paths in a second launch.** `downlight C:notes.md` in a second launch resolves against the running process's current folder on that drive, not the second launch's. Decide whether to resolve it in the second launch before handing it over, or say it can't be opened. **Decided:** the second launch makes the path absolute against its own current folder before handing it over.
- [x] **Dropping a shortcut.** Dropping a `.lnk` to a Markdown file says "Downlight opens Markdown files". Decide whether to follow the shortcut (through the shell, never running it) or name shortcuts in the message. **Decided:** shortcuts are not followed; the notice for a dropped `.lnk` says to drop the file itself, not its shortcut.
- [x] **Line numbers in raw HTML.** A document's raw HTML may carry its own `data-sourcepos`, giving its blocks false line numbers that reload anchoring and Find's first match then use. Decide whether to drop the attribute from raw HTML (in the same pass that renames filtered tags in `core/src/sanitize.rs`) or accept it as the document's own doing. **Decided:** the sanitizer drops `data-sourcepos` from the document's own HTML; only the core's line numbers remain.
- [x] **Mapped drives and shares.** A document on a mapped drive (`Z:`) keeps its relative local images, while the same document opened by its UNC path loses them (images on shares never load). Decide whether that difference is fine or whether drive letters on network drives count as shares too. **Decided:** the difference is accepted: a mapped drive is one the reader connected to on purpose, so loading from it reaches no new host. The glossary's Network share entry says so; nothing else changes.

**2026-11-19, built.** All five, each test-first. `npm run check` passes; `npm run fixtures` changed nothing (no fixture has raw HTML line numbers, and no shape between the page and the app changed).

- **Text and binary files.** The core tells them apart: `is_text` in `core/src/format.rs` calls a file binary when a zero byte comes in its first 8000 bytes (`TEXT_CHECK_LENGTH`), as Git tells it, unless it starts with a byte order mark, since UTF-16 has a zero byte in every ASCII character. Text in UTF-8 or Windows-1252 has no zero byte, and images, programs, archives and Office files have one in their first bytes. UTF-16 without a byte order mark counts as binary, as decoding couldn't read it anyway. `render` (`core/src/render.rs`) now returns `Result<RenderedDocument, RenderError>` and refuses a binary file with `RenderError::NotText`, so no caller can render one; it looks at those 8000 bytes once, whatever the document's size.
  - The app's read (`read_and_render` in `app/src/render.rs`) turns the refusal into `DocumentError::NotRendered`, whose notice is `not_text`: "**a.png** in C:\docs isn't a text file. Downlight opens text files." That covers the command line (the new window shows it in place of the document, as it shows a missing file), a link to a binary `.md`, Back and Forward, and a document whose file became binary since.
  - Open and a drop refuse a binary file before the window is given it, so the window keeps its document and shows the same words as a notice (`app/src/open.rs`): `is_text_file` reads only the file's first 8000 bytes, on the blocking thread that already serves the dialog and the drop. A file whose start can't be read is given anyway, so the window tells why it can't be read, as before. Open's dialog starts filtered to "Markdown files" and has "All files" (`*`, which rfd 0.18 writes as `*.*`, matching every file, one without an extension too); `show_chosen` shows the choice. A drop shows its first text file, whatever its extension.
  - Links are unchanged: a link shows only a Markdown file as a document and reveals any other file (`is_markdown`, kept for links, the dialog's filter and the installer).
- **Drive-relative paths.** tauri-plugin-single-instance 2.5.5 hands a second launch's arguments over as the process got them (it reads `std::env::args_os()` itself, with the current folder alone) and offers no hook to change them, so the second launch can't make them absolute inside the handover. Instead `main` asks `command_line::relaunch_paths` first thing: when an argument is drive-relative (`C:notes.md`, a drive letter without a root), every path is made absolute in this process, which knows its own current folder on each drive (`std::path::absolute`, which is `GetFullPathNameW`), and `command_line::relaunch` starts Downlight again with the whole paths, and this launch exits. The new launch hands them over, or is the first instance itself. A path that can't be made whole gives no relaunch, so a launch never starts itself again with the same arguments; if the relaunch can't start, the launch goes on as before. Only a launch with a drive-relative path pays the extra process start.
- **Shortcuts.** A dropped `.lnk` (`is_shortcut` in `app/src/open.rs`, by its extension in any case) is never followed nor read. A drop with no text file but a shortcut says "**notes.md.lnk** in C:\Users\me\Desktop is a shortcut. Drop the file itself, not its shortcut."; that comes before the binary file notice, since dropping the file itself is all it takes. A drop of folders alone says "Downlight opens text files."

It scans only the raw HTML, once; the test documents of `npm run measure` have no raw HTML and the binary check is a fixed 8000 bytes, so no work of a document's size changed on them, and it wasn't measured.

**2026-11-19, review fixes.**

- **The relaunched window comes to the front.** The relaunch for a drive-relative path is started by the first launch, which has no window, not by the shell. Windows lets a process take the foreground when the foreground process started it, so the relaunch's window could come up behind the Command Prompt; and as a second launch, the single-instance plugin's `AllowSetForegroundWindow` for the running process runs in the relaunch, which can hand on only a right it holds ([AllowSetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-allowsetforegroundwindow), [SetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow), checked on 2026-11-19). `command_line::relaunch` now calls `platform::let_take_foreground` with the new process's ID right after starting it, before the first launch exits: on Windows that is `AllowSetForegroundWindow` (`app/src/platform/windows.rs`), which Windows refuses when the first launch may not take the foreground either, and then the window comes up as before. Other systems' fallback does nothing (`app/src/platform/mod.rs`). No test can observe the foreground; hand check 6 now checks the window comes to the front.
- **The scan for raw HTML line numbers reads markup as the HTML parser does.** The review found two ways a document's own `data-sourcepos` got past the scan. First, it skipped `<!` and `<?` without reading to their end, so a quote inside a comment, a CDATA, a processing instruction or an end tag's value (`<!-- <a title=" -->`) opened, for the scan, a value that swallowed the real tag after it. Second, it read each raw HTML node on its own, but the parser reads on into comrak's markup: a node that ended inside a tag (`<div title='` and a blank line, or a bare `<div`) made the next paragraph's text, or comrak's own `data-sourcepos`, that tag's attributes. `drop_from_raw_html` in `core/src/sanitize.rs` now runs `line_numbers_and_unfinished_markup` (which replaces `line_number_attributes`) before the renaming of filtered tags. It follows the WHATWG tokenizer: start and end tags with their quoted values (`tag_end`), comments with their ends `-->`, `--!>`, `<!-->` and `<!--->` (`comment_end`), DOCTYPEs and bogus comments (`<!x`, `<?`, `</1`) to their first `>`, and CDATA, which ends at `]]>` in `svg` and `math` and at the first `>` elsewhere: where those differ, the CDATA's `<` is escaped, as the scan can't tell which the parser reads. Raw text elements need no reading of their own, since each is a filtered tag and renamed. A node that ends inside markup (a tag with an open quote or no `>`, a comment without its end, a bogus comment without its `>`) has that markup's `<` and every `<` after it in the node escaped as `&lt;`, so each node ends where the parser reads text. This changes rendering for broken HTML only: **raw HTML that ends inside a tag, a comment or a declaration now shows that markup as text** (an unclosed `<!--` used to hide the rest of its block, or of the document, and now shows it as text). Inline raw HTML can end inside markup too: comrak takes `\v` as a space between attributes, the parser doesn't, so comrak's one tag `<a\vb=">" c="<!--">` ends at its first `>` for the parser and leaves a comment open. The scan edits only by putting `dropped-` before a name or escaping a `<`, reads each node once (`FirstClose` keeps a run of CDATA from reading up to the same `>` again), and the documents of `npm run measure` have no raw HTML, so it wasn't measured. `npm run fixtures` would change nothing: the fixture test passes.
- **Tests.** `core/src/sanitize.rs`, each failing before the fix: `line_numbers_after_comments_and_declarations_are_dropped`, `comment_ends_where_the_html_parser_ends_it`, `line_number_after_cdata_that_svg_reads_differently_is_dropped`, `raw_html_ending_inside_a_tag_shows_the_tag_as_text`, `unfinished_tag_takes_no_line_number_from_the_paragraph_after_it`, `raw_html_ending_inside_a_comment_hides_no_line_number_after_it`, `raw_html_ending_inside_a_declaration_hides_no_line_number_after_it`. The test helpers that turned a refusal to render into HTML text now fail loudly: `html_with` in `core/src/image.rs` unwraps (its module is now `#[cfg(test)] #[cfg(windows)]`, since Clippy's allows for tests don't see `cfg(all(test, windows))`), and `render_block` in `core/tests/highlight_cost.rs` expects with its own `#[allow(clippy::expect_used)]`.

**2026-11-19, after the review, decided by the repo owner.** All three choices the build made stay as built:

- Raw HTML that ends inside a tag, comment or declaration shows that markup as text, though GitHub hides what follows an unclosed `<!--`. The difference is accepted so that no document can give its blocks its own line numbers, and a typo can't hide the rest of the document.
- A launch with a drive-relative path (`C:notes.md`) makes it absolute and relaunches Downlight with it, a first launch too. The extra process start is accepted, since the single-instance plugin offers no other way to meet the decision above.
- A binary file from the command line opens a window that shows the refusal in place of the document, as a missing file does; Open and a drop refuse before the window changes, with a notice.
