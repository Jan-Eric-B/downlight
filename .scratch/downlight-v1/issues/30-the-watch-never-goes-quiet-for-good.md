# 30: A document's watch never goes quiet for good

**What to build:** A window notices every change to its document's file, even when the file system watch stops or misses events, and the reader is told when a file can't be watched. Today the watch can stop without a word, and then saves never reload the document again.

Spec: [Downlight v1](../spec.md)

**Blocked by:** none

**Status:** ready-for-human

- [x] Research first, recorded in this ticket: what notify 8.2.2 does on Windows when the watched folder is deleted, moved or recycled; when `ReadDirectoryChangesW` completes with an error (for example a share's session dropped after sleep or a VPN reconnect); when its buffer overflows; and when re-arming fails. Read from notify's source and Microsoft Learn; check the cases that need a real file system in the release build.
- [x] The window checks the file's stamp again when it gets the focus, and reloads (or shows the bar) when it differs, whatever the watch said. This catches every missed event at the moment the reader looks.
- [x] After `Gone`, the watch keeps looking for the document's folder and file, and reports `Back` when the file returns, even if its folder was deleted and recreated in between (a build that wipes its output folder, a branch switch). Story 40.
- [x] A watch that stops (notify unwatches the folder) is noticed and restarted, or the reader is told that only F5 reloads the document.
- [x] A save made between the render ahead's read and the start of the watch reloads the document. Today the stamp is taken after `watcher.watch`, so a save before the watch gives no event and a save between the watch and the stamp matches the stamp.
- [x] A folder over 260 characters is watched, or the reader is told why not (the manifest has no `longPathAware`).
- [ ] Checked by hand: renaming or deleting the document's folder, or a parent, in Explorer while the window is open. If the open directory handle blocks it ("folder in use"), find a way that doesn't, or record why it must.
- [x] Tested first where a test can observe it: in `app/src/watch.rs` with real temporary folders, a folder deleted and recreated, renamed away and back, and a save while the watch starts.

## Comments

**2026-11-13, from the architecture review.** `app/src/watch.rs` counts a watcher error as a touch (`event.as_ref().map_or(true, ...)`), but notify 8.2.2 never calls the handler with one in these cases. In `src/windows.rs`: on `ERROR_ACCESS_DENIED` with the folder gone it unwatches silently (lines 366-374); on any other error it logs and unwatches (378-388). On a buffer overflow `ReadDirectoryChangesW` succeeds with no bytes, which notify parses as nothing.

**2026-11-17, research.** Read from notify 8.2.2's `src/windows.rs` (the version in `Cargo.lock`) and Microsoft Learn ([ReadDirectoryChangesW](https://learn.microsoft.com/windows/win32/api/winbase/nf-winbase-readdirectorychangesw), [Maximum Path Length Limitation](https://learn.microsoft.com/windows/win32/fileio/maximum-file-path-limitation), and MS-FSA's [FileRenameInformation](https://learn.microsoft.com/openspecs/windows_protocols/ms-fsa/87f86c9b-6c2a-4803-84b7-131a74a434fa) and [open files under a directory](https://learn.microsoft.com/openspecs/windows_protocols/ms-fsa/133840e4-778e-44ca-9b41-da2323615075)).

- **How notify watches.** `add_watch` opens the folder with `CreateFileW(FILE_LIST_DIRECTORY, FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE, FILE_FLAG_BACKUP_SEMANTICS | FILE_FLAG_OVERLAPPED)`, passing the path as given, and keeps one `ReadDirectoryChangesW` (16 KB buffer, completion routine) in flight, re-armed from the completion routine before the buffer is parsed. Its handler is never called with an error on Windows: every failure below is silent.
- **Folder deleted.** The pending read completes with `ERROR_ACCESS_DENIED` (the folder is delete pending). notify checks whether the folder's path still exists: if not, it unwatches (closes the handle) without a word; if something is at that path again already (a build that wiped and recreated it within those milliseconds), it re-arms on the old handle, which fails, and the watch is dead while still registered. Either way no event ever comes again for that path. The file's own deletion comes first as an event, so `Gone` was reported, but `Back` never was.
- **Folder moved or recycled.** Explorer's Delete moves the folder into `$Recycle.Bin`, a rename. ReadDirectoryChangesW "does not report changes to the specified directory itself", and the handle follows the folder to its new place: no error, no event, and later events from the moved folder arrive under the old path. So the document's `Gone` was never reported, and if the folder came back (Restore), the old handle happened to work again. Emptying the Recycle Bin then deletes it, as above.
- **Completion with another error** (a share's session dropped after sleep or a VPN reconnect gives a network error such as `ERROR_NETNAME_DELETED`; `ERROR_NOTIFY_ENUM_DIR` when the system couldn't record all changes): notify logs it and unwatches. Silent and for good.
- **Buffer overflow.** The read succeeds with zero bytes and "the entire contents of the buffer are discarded"; notify parses its zeroed buffer as one entry of no action and emits nothing. The changes in that burst are lost, but the watch goes on.
- **Re-arming fails** (`ReadDirectoryChangesW` returns 0, as on a handle whose folder is gone): notify frees the request and releases its semaphore, and the watch stays registered but dead. Silent and for good.
- **Long paths.** `CreateFileW` takes a path over 260 characters only with the `\\?\` prefix, or when the process's manifest has `longPathAware` and the machine's `LongPathsEnabled` registry value (or group policy) is 1; both are needed, so the manifest alone wouldn't do. notify passes the path as given, so a long folder failed to watch.
- **Explorer and the handle notify holds.** The share mode lets others read, write, delete and rename the watched folder itself: renaming a directory fails only for open files and folders inside it (MS-FSA 2.1.5.15.12 with 2.1.4.2), and the folder's own handle isn't one. But renaming, moving or recycling any parent of the watched folder must fail with `STATUS_ACCESS_DENIED` while the handle is open, whatever its share mode: 2.1.4.2 walks every folder below the one renamed and denies on any open, after first breaking batch or handle-caching oplocks on them. Explorer shows that as "The action can't be completed because the folder or a file in it is open in another program". Any program that watches folders this way (VS Code, for one) blocks the same.
- **Checked on a real file system** (NTFS, by the tests in `app/src/watch.rs`): deleting and recreating the folder (after which the old watch sees nothing of the new folder, so it stands in for every change the watch misses), renaming it away and back, and a folder over 260 characters. A write through a hard link in another folder was tried as a stand-in too, but the document's folder now and then gets an event for it after all (most likely a scanner opening the file by its other name, which refreshes that name's directory entry), so it is no test. A share's session dropping and Explorer's dialogs are hand checks below.

**2026-11-17, built.** The watch checks the file itself whenever the folder's events can't be trusted, and starts the folder's watch again when they failed.

- **A check every 2 seconds and on focus** (`app/src/watch.rs`). The watch's thread now owns the folder's notify watcher. Besides waiting for events, it compares the file's stamp with the last one every `RECHECK` (2 s) and when `Watch::recheck` asks. `Documents::activated`, which runs on `WindowEvent::Focused(true)`, calls it for the window's watch, so a missed change reloads the document (or shows the bar) the moment the reader looks. A change a check finds goes through the same 150 ms quiet wait as an event, so a file still being written is read once it is done.
- **Started again.** A change found by a check rather than an event means the folder's events missed it, so the folder is watched anew (the new watcher starts before the old one goes). A `Gone` whose folder is gone drops the folder's watch, since a deleted folder's has stopped and a moved one's follows it elsewhere; while the folder is missing each check looks for it, and once it is back it is watched again. So after a folder is deleted and recreated, or renamed away and back, `Back` comes within one check and later saves are reported by their events again.
- **The read's stamp** (`app/src/render.rs`, `app/src/documents.rs`, `app/src/documents/watching.rs`). The render ahead now takes the file's stamp just before its read (`render::start_with_stamp`) and hands it to the watch through a channel kept on the shown document; the watch starts from it, and its first act is a comparison after the quiet wait, so a save at any time after the read reloads the document.
- **Long folders.** notify is given the folder's canonical path, which on Windows is the `\\?\` form, so a folder over 260 characters is watched without the manifest or the registry. A folder that can't be canonicalized (some virtual drives) is watched as named.
- **The notice.** A missing folder is no longer a watch that can't start: the window waits for it (story 40), and the reader isn't told anything. A folder that is there but whose events can't be watched (a share or file system without change notifications) is still checked every 2 s, and the held notice now says so: "Can't watch **doc.md** for changes as they are made, so a save reloads it up to 2 seconds later: ...". The contract samples carry the new wording (`npm run fixtures`).
- **Tests**, written first. In `app/src/watch.rs`, with real temporary folders: `save_between_the_read_and_the_start_of_the_watch_reports_changed`, `folder_deleted_and_recreated_reports_gone_then_back_then_saves`, `watch_started_again_once_its_folder_is_back_reports_saves_by_their_events` (checked only by a recheck, so the last save can only come by events), `folder_renamed_away_and_back_reports_gone_then_back`, `recheck_of_an_unchanged_file_reports_nothing` and `folder_over_260_characters_reports_saves_by_their_events`. A test-only `Watch::start_checking_every` sets how often the file is checked, so a test can tell what events report from what checks find. In `app/src/documents/tests/watch.rs`: `document_whose_folder_is_missing_is_asked_for_again_once_its_file_is_written` replaces the test of a notice for a missing folder, and `window_getting_the_focus_reloads_a_file_its_watch_missed` (the folder deleted and made again, then the focus well inside the 2 s check; it fails without the recheck). The focus check lives in the app, so the page and its contract didn't change and there is no page test.
- **Decisions taken by default.** The check runs every 2 s: one metadata call per window, beside notify's own thread, which wakes every 100 ms; a missed save then reloads at most 2 s late, and at once on focus. The check runs for a document on a share too, since the window reads that file anyway. A file that can't be looked at (an offline share) counts as gone, as before, so the bar shows and `Back` reloads it when the share returns. The work doesn't grow with the document's size, so there is no new measurement; the render ahead takes one more metadata call before its read.

**2026-11-17, hand checks for the owner.** On the release build (`npm run tauri build`), with a document open in a window:

1. Rename the document's own folder in Explorer. Expected: allowed (the watch's handle shares delete, and the folder's own handle doesn't count). Within about 2 s the window shows "File deleted or moved". Rename it back: within about 2 s the document reloads at the same reading position, and a save after that reloads at once.
2. Delete the document's folder with Delete (to the Recycle Bin). Expected: allowed, as in 1, and the bar within about 2 s. Restore it from the Recycle Bin: it reloads within about 2 s.
3. Delete the folder with Shift+Delete, then create it again with the file in it (copy it back, or run a build or `git checkout` that writes it). Expected: the bar at once (the file's deletion is an event), and the document back within about 2 s of the file being written. Saves after that reload at once.
4. Rename, move or delete (to the Recycle Bin) a parent of the document's folder, one or two levels up. Expected from MS-FSA: blocked with Explorer's "folder or a file in it is open in another program" for as long as the window is open; closing the window lets it through. See the question below.
5. Switch the window away and back without saving: nothing reloads, and the reading position stays. Then, with another window in front, Shift+Delete the document's folder and copy it back, and click the Downlight window right away: it reloads as it gets the focus, rather than up to 2 s later.
6. A document on a network share: sleep the computer or reconnect the VPN, then save the document from the editor. Expected: the first save reloads within about 2 s (the folder's watch may have stopped), and the saves after it at once again.
7. A document in a folder whose path is over 260 characters (made with `git clone` into a deep folder, or `robocopy`): saves reload at once, and no notice shows.

**Open for the owner** (from hand check 4): if a parent folder can't be renamed while the window is open, the one way around it found is to hold the folder's handle with a handle-caching oplock (`FSCTL_REQUEST_OPLOCK`, directory oplocks since Windows 8), which a rename of a parent breaks before it is denied (MS-FSA 2.1.4.2); the watch would then close the handle and rely on its 2 s check until the folder can be watched again. notify has no such mode, so it means a `ReadDirectoryChangesW` watch of Downlight's own in the per-OS module (`unsafe`). The alternative is to accept the block, as VS Code and other folder watchers do, and say so.

**2026-11-17, decided by the repo owner.** The block on renaming, moving or recycling a parent of the document's folder is accepted, as VS Code and other folder watchers have it, and the spec's Watching now says so. No watch of Downlight's own with a directory oplock is planned. Hand check 4 confirms the block and that closing the window lets the rename through.

**2026-11-17, decided by the repo owner, from the review.** When a folder that was missing comes back but its changes can't be watched (a share or file system without change notifications), the window shows the same notice as when a watch can't start ("Can't watch **a.md** for changes as they are made, so a save reloads it up to 2 seconds later: ..."), once. The watch keeps its special case for a missing folder, so a document whose folder comes back reloads as soon as its file is written rather than at the next 2 s check (story 40). To be built with the review fixes.

**2026-11-17, review fixes.** From the codebase design and thermo-nuclear reviews of the build, and the owner's decisions on them.

- **The read stamp** (`app/src/watch.rs`, `app/src/render.rs`, `app/src/documents.rs`). The stamp the render ahead takes just before its read now reaches the watch as one type of the watch's own, `watch::ReadStamp`, made in a pair with the `ReadStampNoter` the render task notes it with. `Stamp` is private to the watch again. `render::start` is the one way to start a read and render, and gives the stamp too; a Reload and a render the page asks for drop it, since the watch runs already. The watch waits for the stamp on its own thread, not on a pool thread. If the render task panicked or never ran, so the stamp was never noted, the watch starts from the file as it is then.
- **A watch that starts at once** (`app/src/watch.rs`, `app/src/documents/watching.rs`). `Watch::start` only starts the watch's thread, which watches the folder first thing. What the watch tells its window is a `Report`: a `Change`, or that the folder's events can't be watched, with why and how often the file is checked. So `Documents::watch` starts the watch under the lock that finds the window still showing the document. The blocking thread it used to start on, the step that kept a watch that started late, and the race of a watch started after the window left the document are gone. A folder deleted while its watch starts counts as missing, not as one whose events can't be watched.
- **The notice when a folder comes back** (owner's decision above). The watch reports that the folder's events can't be watched whenever the folder's watch fails to start, once in each run of failed tries: when the watch starts, and when a missing folder comes back. The window shows the same "Can't watch **a.md** for changes as they are made, so a save reloads it up to 2 seconds later: ..." notice, held until the page first asks, as before. The special case for a missing folder stays, so a document whose folder comes back reloads as soon as its file is written.
- **Smaller fixes.** `FolderWatch::start` gives an error instead of a pair, and no error is dropped. The thread's loop waits for quiet, reports, then waits for a change, without a flag. The comment on `Watch`'s channel says why it never closes while the thread runs (the thread holds a sender of its own), and the arms for a closed channel stay, commented, so the loop can't spin.
- **Tests.** Added, written first and failing before the change: `folder_back_but_its_events_cannot_be_watched_reports_so_once` in `app/src/watch.rs`. Added: `folder_whose_events_cannot_be_watched_reports_so_once_and_saves_by_its_checks` in `app/src/watch.rs`; both hold the folder open without sharing it, so it is there but notify can't open it, as on a share without change notifications. Added: `folder_whose_events_cannot_be_watched_tells_the_reader_saves_reload_late` in `app/src/documents/tests/watch.rs`, which checks the notice's wording. Removed: `watch_for_a_document_the_window_has_left_is_dropped`, since a watch can no longer start late. Changed: `window_forgotten_before_its_page_asks_hands_over_nothing_and_drops_its_late_watch` keeps only its handover and is now `window_forgotten_before_its_page_asks_hands_over_nothing`. The watch tests' helpers take a `ReadStamp` and fail on any report but a change.
