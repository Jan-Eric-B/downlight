# 09: Opening from inside a window

**What to build:** From inside a window, Ctrl+O and dropping a file show a document there, and a window started without a file offers "Open file" and says that a file can be dropped. This ticket also creates the right-click menu on the document, which later tickets fill with their own commands.

Spec: [Downlight v1](../spec.md)

**Blocked by:** 08 (One process, a window per document)

**Status:** ready-for-agent

- [x] Ctrl+O shows an open dialog filtered to `.md`, `.markdown`, `.mdown`, `.mkd`, `.mkdn` and `.mdwn`, and shows the chosen document in this window. If the document is open in another window, that window comes to the front instead.
- [x] Dropping a Markdown file onto a window shows it there, by the same rule.
- [x] Dropping anything else shows a short message saying that Downlight opens Markdown files.
- [x] A window started without a file shows "Open file" and "or drop a file here".
- [x] Right-clicking the document opens a native menu with Open and Copy, and Ctrl+C copies the selection.
- [x] Later tickets can add a command to the menu in one place.

## Comments

**2026-11-03, review.** In the walking skeleton, the render command (`render_document` in `app/src/document.rs`) reads the one process-wide `CommandLineDocument`. Here a window's document changes with Ctrl+O and dropping, and a window can start without one, so the render command reads the document of the window that calls it, from the per-window state ticket 08 adds. The render command moves into its own module, which finishes splitting `app/src/document.rs` by feature.

**2026-11-03, review of ticket 08.** `OpenWindows` (`app/src/window.rs`) records a window's document once, when the window is claimed, and a window without a document gets a label but no entry (`claim_empty`, and a branch of its own in `open_launch`). Here a window's document changes, so start by recording every window with the document it shows now, if any, and one way to change it (Ctrl+O, dropping, and later links and Back). An empty launch is then a window that shows nothing yet, and `claim_empty` and its branch go away. The key that finds an open document has to follow the change, so that opening it again brings this window to the front.

**2026-11-03, architecture review.** Today the rule "a document is shown in at most one window" is split between `OpenWindows` and its caller: after `Claim::New` the caller has to `forget` the label if the window fails to build, an empty launch takes `claim_empty`, and the title comes from `title_of` on the side. Ctrl+O and dropping (and later links and Back) would each repeat those steps. Start this ticket by giving `OpenWindows` one call that takes a document and a target (a new window, or a given window) and returns "shown here" or "already open in window X", updating the window's entry, its key and its title under the one lock. A window that fails to build gives its label back on its own (for example through a guard), so no caller has to remember to. The claim tests carry over and still need no window, since the only outside dependency is the file system. Expected size: about 100 changed lines in `app/src/window.rs`.

**2026-11-09, implementation.** `window::show(app, document, target)` is the one way a window gets or changes its document, for a new window (launches) or a given one (Open, dropping, later links and Back). Under one lock, `OpenWindows::claim` records every window with the document it shows now (`None` while empty), finds a document that is open already, and gives the title. `show` then opens the window, or sets the title and sends the page `document-shown`, or brings the other window to the front. An empty launch is `show(app, None, NewWindow)`, so `claim_empty` and its branch are gone. Instead of a guard, `show` itself gives back the label of a window that fails to build, since it is the only place a window is built. The render command moved to `app/src/render.rs` and returns `None` for a window without a document, which the page shows as the empty state. The core has the Markdown rule (`is_markdown`, `MARKDOWN_EXTENSIONS`, `core/src/format.rs`) for the dialog's filter, dropping and later ticket 11. `npm run check` passes.

- **The page owns the commands.** `page/src/commands.ts` lists each command's id, menu text, shortcut and action; a later ticket adds its command there and to the `menu` list beside it, and nowhere else. On a right-click the page sends the menu's lines to `show_document_menu`, which shows them as a native menu (`app/src/menu.rs`). Tauri reports a menu choice to the whole app with only the item's id, so ids are `<window>/<command>`, and `forward_choice` sends `menu-command` to that window's page, which runs the command. Copy is muda's own Copy item, which on Windows sends Ctrl+C to the webview, so it copies with formatting. Ctrl+W moved into the same table.
- **The app talks to the page with events**: `document-shown`, `menu-command` and `notice`. Listening is a plugin command, so `app/capabilities/document-windows.json` grants `core:event:allow-listen` and `allow-unlisten` to `document-*` windows, and nothing else. The page listens through `listenToApp` (`page/src/events.ts`), on its own window: Tauri delivers an event sent to one window only to listeners that name that window, never to a plain `listen`. The mocks don't model this, so `events.test.ts` checks the target.
- **Open dialog**: `rfd` 0.18.0 (MIT) without default features, rather than `tauri-plugin-dialog`, which would also bring `tauri-plugin-fs` and need a capability. On Windows rfd needs only `log`, `raw-window-handle` and `windows-sys` 0.61, all in the tree already. The dialog belongs to the window and runs on a blocking thread.
- **Dropping** is handled in Rust (`WindowEvent::DragDrop`), so no path passes through the page. The first Markdown file of a drop is shown; a drop without one gives the notice "Downlight opens Markdown files (.md, .markdown, .mdown, .mkd, .mkdn, .mdwn)."
- **A trap with `removeUnusedCommands`**: the list of plugin commands to keep is written into the `tauri` crate's build output, and Cargo doesn't rebuild that crate when a capability changes. The first release build after adding the capability still had `listen` compiled out ("Command listen not found" in the window). After changing a capability, run `cargo clean -p tauri --release` before `npm run tauri build`.
- `cargo audit`: no advisories for rfd. Five warnings remain, all for Linux-only crates in Tauri's tree (glib, zbus).
- Checked by hand on the release build, with WebView2's remote debugging to read the page: an empty launch shows "Open file" and "or drop a file here" titled Downlight; Ctrl+O shows the dialog filtered to "Markdown files", and the chosen README shows in that window with its title; choosing `NOTES.md` in one window while `notes.md` is open in another brings that window to the front and leaves the first as it was; the right-click menu shows "Open... Ctrl+O" and "Copy Ctrl+C"; Open in the menu shows the dialog; Copy in the menu and Ctrl+C both copy the selection; Ctrl+W closes each window and the process exits with the last. In dark mode only.
- Still to check by hand: dropping a `.md` file, a `.txt` file and a folder onto a window (dropping couldn't be driven from a script); the empty state and the notice in light mode.
