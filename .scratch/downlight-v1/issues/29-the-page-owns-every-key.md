# 29: The page owns every key

**What to build:** WebView2's browser keys are turned off as a whole, and the page's command table becomes the one place that says which key does what. Today the keys the page handles are listed twice, in the page's command table and in the app's WebView2 key handler, and tickets 12 and 16 would each extend both.

Spec: [Downlight v1](../spec.md)

**Blocked by:** none

**Status:** ready-for-human

- [x] The app sets `AreBrowserAcceleratorKeysEnabled` to false on each webview (`ICoreWebView2Settings3`). Microsoft documents that this turns off Find (Ctrl+F, Ctrl+G, F3), every reload (F5, Ctrl+R, Ctrl+F5, Shift+F5, Ctrl+Shift+R, the Refresh key), zoom (Ctrl+plus, Ctrl+minus, Ctrl+0), Back and Forward (Alt+Left, Alt+Right, the browser keys), Print (Ctrl+P), Downloads (Ctrl+J), caret browsing (F7), Stop (Esc) and DevTools, and keeps Ctrl+C, Ctrl+X, Ctrl+V, Ctrl+A, Ctrl+Z and the movement keys ([Differences between Microsoft Edge and WebView2](https://learn.microsoft.com/microsoft-edge/webview2/concepts/browser-features#additional-keyboard-shortcuts-information)).
- [x] `leave_reload_and_find_keys_to_the_page`, `is_reload_or_find_key` and their tests in `app/src/platform/windows.rs` go. A setting that can't be applied doesn't fail the window, as today.
- [x] Dev builds keep the DevTools keys (F12, Ctrl+Shift+I), for example by enabling those keys alone through `IsBrowserAcceleratorKeyEnabled`.
- [x] `Command` in `page/src/commands.ts` takes a key with its modifiers, replacing `ctrlLetter`, `key` and `shift`, so Alt+Left (ticket 12) and Ctrl+plus (ticket 16) fit without a special case. The menu shows each command's shortcut from it. `isWebviewReload` goes if nothing is left for it to swallow.
- [ ] Checked by hand in the release build: Ctrl+P, Ctrl+J, F7 and Esc do nothing of WebView2's own; Ctrl+F, F3, F5, Ctrl+R and Ctrl+Shift+R do only the page's; Ctrl+C and Ctrl+A still work in the document and in the find box; zoom keys do nothing until ticket 16 gives them commands. Ctrl+wheel is a separate setting (`IsZoomControlEnabled`) and the mouse's side buttons aren't keys; note what they do.

## Results

Built 2026-11-16. Clippy, cargo-deny, ESLint, `cargo test --workspace` and the page's command tests pass, and this ticket's files are formatted. The full `npm run check` didn't pass while this was built, only because of another ticket's work in progress in the same tree (notices naming their file: rustfmt in `app/src/links.rs`, `notice.rs`, `open.rs` and `render.rs`, `tsc` in `page/src/view.ts`, and two notice tests in `page/src/contract.test.ts`); none of those failures is in this ticket's files. Run it again once that work lands.

**Beyond the plan:**

- `leave_reload_and_find_keys_to_the_page` is now `platform::leave_keys_to_the_page`, which does two things: it sets `AreBrowserAcceleratorKeysEnabled` to false (`ICoreWebView2Settings3`), and it adds an `AcceleratorKeyPressed` handler that sets `IsBrowserAcceleratorKeyEnabled` on every browser key, false unless the key is a DevTools key in a debug build. The handler isn't only for dev builds: Tauri reaches the webview (`with_webview`) only after wry has started loading the page, and Microsoft documents that a setting changed after `NavigationStarting` applies only from the next top-level navigation (`CoreWebView2Settings`), which in a release window never comes. The handler's per-key switch overrides the setting and holds at once (Microsoft's `IsBrowserAcceleratorKeyEnabled` docs), and it lists no keys of its own: WebView2 raises the event for every browser key, so a key a later WebView2 adds is off too. Tauri doesn't expose wry's `with_browser_accelerator_keys`, which sets it before the page loads. A failure to change the setting or add the handler is ignored, as before.
- Dev builds are `cfg!(debug_assertions)`: wry turns DevTools on in debug builds only (`devtools` defaults to `debug_assertions`, and the app doesn't enable Tauri's `devtools` feature). The keys are F12 and Ctrl+Shift+I, checked by the pure `is_dev_tools_key`, with tests `dev_tools_keys_are_f12_and_ctrl_shift_i` and `other_keys_are_not_dev_tools_keys`. Ctrl+Shift+J and Ctrl+Shift+C, which WebView2 also counts as DevTools keys, stay off.
- `Command` has `shortcuts`, a list of `{ key, ctrl?, alt?, shift? }`, each pressed with exactly the modifiers it names (Meta never). Reload's F5 and Ctrl+R are two entries of one list; ticket 12's Alt+Left with the BrowserBack key, and ticket 16's Ctrl+plus with its spellings (`+` with or without Shift, `=`), fit the same way. A lower-case letter follows the layout as `ctrlLetter` did (the letter typed on a Latin layout, the key's place on others); any other key is `KeyboardEvent.key` as is. The menu and the tooltips show the first entry, modifiers in the order Ctrl, Alt, Shift, a letter in upper case and a named key as `KeyboardEvent.key` names it.
- `isWebviewReload` is gone: with the browser keys off, Ctrl+F5, Shift+F5 and Ctrl+Shift+R reload nothing, and the page gives them no command. Its test is now "Ctrl+F5 / Shift+F5 / Ctrl+Shift+R does nothing" (no request to the app, and the key isn't cancelled). Commands still cancel their keys, repeats too, for webviews whose browser keys are on: other systems' until their ports, and a window whose keys couldn't be turned off.
- Ctrl+wheel: Tauri leaves `zoom_hotkeys_enabled` false by default, so wry already sets `IsZoomControlEnabled` and `IsPinchZoomEnabled` to false on every window, and this ticket changes nothing there.

**Not yet checked by hand** (release build, `npm run tauri build`): Ctrl+P, Ctrl+J, F7 and Esc do nothing of WebView2's own; Ctrl+F, F3, Shift+F3, F5, Ctrl+R open Find, step and reload only the page's way, and Ctrl+Shift+R, Ctrl+F5, Shift+F5 and the Refresh key do nothing; Ctrl+C and Ctrl+A work in the document and in the find box; Ctrl+plus, Ctrl+minus and Ctrl+0 do nothing; Ctrl+wheel (expected: nothing, see above); the mouse's side buttons (note what they do; with one page and no history WebView2 has nowhere to go); and in `npm run tauri dev`, that F12 and Ctrl+Shift+I still open DevTools while F5 still reloads only the document. Above all, that the handler holds on the first page, which is the point of having it.

## Comments

**2026-11-13, from the architecture review.** Ticket 10 kept WebView2's zoom keys on purpose, which was the reason to turn off only some keys. Ticket 16 takes zoom over and lists this as its option 2, so that reason goes. Ctrl+P, Ctrl+J, F7 and Esc still reach WebView2 today: Ctrl+P opens its print dialog, which the spec only plans for v1.x, and then as a command of the page's own.
