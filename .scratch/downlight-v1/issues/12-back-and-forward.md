# 12: Back and Forward

**What to build:** Each window remembers the documents and headings visited in it, and Back and Forward move through them, each step returning to where the reader was. The history belongs to its window and disappears when the window closes.

Spec: [Downlight v1](../spec.md)

**Blocked by:** 03 (Page test harness), 09 (Opening from inside a window), 10 (Reload), 11 (Links), 22 (One module owns a window's shown document), 23 (The app decides whether a page shows or reloads its document), 24 (The documents module sends a link's scroll where it decides it), 25 (One pipeline places every document in the page's view), 26 (One message makes the page ask, and every request names its showing), 28 (The documents module carries out the whole show), 29 (The page owns every key)

**Status:** ready-for-human

- [x] Following a link to a document or heading, Ctrl+O and dropping a file each add a history entry in the window.
- [x] Alt+Left and Alt+Right and the mouse's side buttons go back and forward.
- [x] Going back returns to the reading position the document had when it was left.
- [x] History belongs to its window, isn't saved, and is gone when the window closes.
- [x] Back and Forward are in the right-click menu and are unavailable when there is nowhere to go.
- [x] Page tests cover adding entries, going back and forward, and the restored reading position (by line number).

## Results

Built 2026-11-16. `npm run check` passes. The history is split by what each side knows. The app keeps which documents (`app/src/documents/history.rs`): each window's record in the table (`WindowRecord`) holds its shown document and its `History`, the documents before and after it, each kept as the `Showing` it had with its path and key. The page keeps where its view was (`page/src/history.ts`, `WindowHistory`): for each showing, its visits (one when the window showed it, one more for each heading a link scrolled to) with the line number each was left at, and the visit it is at. Back and Forward step through the visits of the showing in view first, with no request to the app and no read of the file, and only past its first or last visit ask the app (`step_history`).

**Beyond the plan:**

- A step is built on `claim` and `change`, as ticket 28 asked: `Documents::step` claims under the lock (`claim_step`), and `carry_out`, which `give` now uses too, titles the window, sends `AskForDocument`, starts the watch, and on failure puts back the whole record, shown document and history, so a step that fails leaves Back where it was. The document stepped to keeps its old `Showing` (`ShownDocument::arrived` with `Arrival::Stepped`), its render starts ahead and its file is watched again. `handover` answers it with the third place, `Place::Return` (`"return"`), timed as `read-and-render`; the page lands at the line its history kept for that showing (`landAtLine`, the same `returnToReadingPosition` a reload uses, from the top), through the same request and its "latest request wins" guard. The ticket 23 rule tested by `window_given_back_a_document_it_showed_before_shows_it_anew` stays for `give` (Ctrl+O, a drop, a link): only a step returns.
- Every `render_document` answer carries `steps` (`{ back, forward }`): whether the app has a document to go back or forward to. With the page's own visits it decides what the menu offers. `MenuEntry::Command` takes `enabled` (a new contract sample, `unavailableCommand`), and a command can say `available()` in `page/src/commands.ts`.
- A heading visited after Back drops what Forward would have gone to, as in a browser. The app doesn't see a scroll within a document, so the page tells it with a second command, `forget_forward`, which names the showing in view and changes nothing for a window that has left it. The page sends it only when the app had somewhere to go forward to.
- Back to a document that another window shows by now brings that window to the front and leaves this window, and its history, where it is, as Ctrl+O does for that document (ADR 0001). Once the other window closes, the step can be taken.
- The page's three ways to a heading: a link's own `scrollTo` and the app's `scroll-to-heading` (a link in another window) both go through `visitHeading` in `page/src/view.ts`, which records a visit only when the document has the heading. A show at a heading is one step, the document's; it records no second one. `scrollToHeading` is now private to the view.
- `ShownReason` has `return` too, so ticket 13 tells a reload from everything else. Of several swaps the listeners hear at once, a show or a return wins over a reload.
- The mouse's side buttons are `mouseButton: 3` and `4` on the Back and Forward entries of the command table, run on `mouseup` and cancelled there (not on `auxclick`, which needs the press and release on one element). `shortcutOf` writes `ArrowLeft` and `ArrowRight` as `Left` and `Right`, so the menu shows `Alt+Left` and `Alt+Right`. The menu is Back, Forward, Reload, Find, then Open, then Copy, in the spec's order.
- The empty state is no step: a window started without a file and given one has nothing to go back to.
- The page keeps the visits of every showing it has seen until the window closes, also of showings the app has since dropped from its history; a few numbers each.
- `documents.rs` would have grown past 1,000 lines, so `WindowRecord`, `History`, `Step`, `Steps`, `StepError` and both commands live in `app/src/documents/history.rs`.

**Tests changed:** the menu test in `page/src/commands.test.ts` ("replaces the webview's menu with Back, Forward, Reload, Find, Open and Copy"), since the menu gains Back and Forward and every entry `enabled`; `shownFrom` in `page/src/title-bar.test.ts` and `heading_of` in `app/src/documents/tests/mod.rs`, for the answer's new `steps` and the new place.

**Measured:** nothing new. Going back reads and renders the document as a show does, and lands with the reading-position code a reload uses, which `npm run measure` times on the 1 MB document (ticket 02 holds the baseline); it has no Back case, and driving one needs the window by hand. A step within a document is a scroll.

**Not yet checked by hand** (release build): Alt+Left, Alt+Right, the BrowserBack and BrowserForward keys and both side buttons go back and forward, and WebView2 does nothing of its own on any of them; Back returns to the line it left on a long document, after a link, Ctrl+O and a drop; a heading link, then Back and Forward, within one document; the menu's Back and Forward unavailable with nowhere to go; Back to a document opened in another window meanwhile brings that window to the front; closing the window and opening the document again starts with no history.

## Comments

**2026-11-12, from ticket 10's code quality review.** What ticket 10 left in place that this ticket builds on:

- The reading position is already a line number. `readingLine(view)` in `page/src/view.ts` gives the line of the block at the top of the view. `blockAt(view, line)`, followed by two `scrollIntoView` calls a frame apart, puts that block back at the top; the second call is needed because `content-visibility` only estimates heights (ADR 0003). Both functions are module-private. Export them, or move them to a `reading-position.ts`, rather than writing a second anchoring. Reload's tests in `page/src/view.test.ts` show how to fake layout (`layOut`, `spyOnScrolls`).
- `whenDocumentShown` runs after every shown document and every reload. If history needs to know why a document was shown, pass the listeners a reason (shown, reload, back, forward) rather than adding a flag beside the hook.
- Alt+Left, Alt+Right, the BrowserBack and BrowserForward keys and the mouse's side buttons trigger WebView2's own navigation, the way F5 and Ctrl+R triggered its own reload. Ticket 10 found that cancelling a key in the page doesn't always stop WebView2 (Ctrl+Shift+R still reloaded). Its fix is the `AcceleratorKeyPressed` handler `leave_reload_keys_to_the_page` in `app/src/platform/windows.rs`. Extend that one handler to the navigation keys, and rename it for what it covers, rather than adding a second handler. Check each key and both side buttons by hand in the release build.
- `Command` in `page/src/commands.ts` has `ctrlLetter`, and `key`, which means a key pressed without modifiers. Alt+Left fits neither. Widen the shape for all commands, for example to a key with its modifiers, rather than adding a special case for Alt.
- In `startDocumentView`, the page's `latestRequest` guard makes the latest request win when a document is shown during a reload, or the other way round. Back and Forward must go through the same guard.

**2026-11-12, from ticket 14's architecture review.** What changed since the comment above, and one thing to do first:

- The reading position now has its own module, `page/src/reading-position.ts`, which replaces the first bullet above. `readingPosition(view)` gives the line number of the block at the top of the view, and `returnToReadingPosition(view, line, stillWanted)` puts the view back there, with the second scroll after a frame that ADR 0003 needs. Reload uses both, so going back uses them too. Don't write a second anchoring.
- Before adding Back and Forward, give `startDocumentView` one request pipeline. Today `showDocument` and `reload` each bump `latestRequest`, check after every `await` whether a newer request overtook them, and must remember to call `announce` on every way out (ticket 14 added it to three exits by hand). Back and Forward would be two more requests written the same way. Make one pipeline that every request goes through (show, reload, back, forward). It owns "the latest request wins", the swap of the view's content, and a single `announce` that passes the listeners a reason (shown, reload, back, forward). Each kind of request then says only how it gets its render and where it lands: at the top or a heading, at the reading position, or at a history entry's line. The swap is also where ticket 13 reads the ticks before the old items go and applies them after.
- `Command` in `page/src/commands.ts` now has a `shift` flag too, for Shift+F3 (ticket 14). Widening it to a key with its modifiers, as the bullet above says, replaces `shift` as well.
- The WebView2 key handler is now `leave_reload_and_find_keys_to_the_page` (ticket 14). When it takes the navigation keys, name it for what it is, the keys the page handles itself, rather than adding "and navigation" to the name, so ticket 16's zoom keys don't rename it again.

**2026-11-13, from the architecture review.** What to settle before building, and where the groundwork now sits:

- Tickets 25, 26, 28 and 29 come first. 25 gives the page's view one pipeline, so Back and Forward are one more way to land (at a history entry's line), and its snapshot before the swap is where an entry's line is saved. 26 makes every page request name its showing. 28 lets `Documents::give` retitle the window itself, which Back needs. 29 makes the page the only owner of keys, so Alt+Left and Alt+Right are entries in its command table and not also in a WebView2 handler.
- History needs a window record that outlives its shown document. Today the table's value is `Option<ShownDocument>` (`app/src/documents.rs`), and every `give` replaces it, so nothing per window survives a document change. Let the table hold a window record: its shown document and the documents and headings visited in it. The app has to hold the paths, since commands never take a path from the page.
- Key each history entry by its `Showing`. Every `give` takes a new one today, so the page has nothing that comes back to key its saved line (and ticket 13's ticks) to. A step back or forward gives the window an earlier entry with that entry's own `Showing`. The page then finds its saved state for it, and `handover` answers with the third `Place` ticket 23 left room for (return to a saved line).
- That changes one rule from ticket 23, tested by `window_given_back_a_document_it_showed_before_shows_it_anew`: for Ctrl+O and links it stays right, for Back it is wrong. Decide this first.
- Scrolling to a heading has three ways in today: the link's own result (`page/src/links.ts`), a show at a heading (`page/src/view.ts`) and the `scroll-to-heading` message. A heading link is a history entry too, so route the three through one scroll that records it.

**2026-11-16, from ticket 29.** WebView2's browser keys are off (`platform::leave_keys_to_the_page`), so Alt+Left, Alt+Right and the BrowserBack and BrowserForward keys reach the page and do nothing of WebView2's own: there is no app handler to extend any more, and the bullets above about `leave_reload_keys_to_the_page` no longer apply. Back and Forward are entries in the page's command table, each with a list of shortcuts, for example `shortcuts: [{ alt: true, key: "ArrowLeft" }, { key: "BrowserBack" }]` (`KeyboardEvent.key` names). The menu shows the first entry as `Alt+ArrowLeft` today, since a named key is shown as `KeyboardEvent.key` names it; give the arrow keys their Windows names (`Left`, `Right`) in `shortcutOf` when the first command with one arrives. The mouse's side buttons aren't keys and the setting doesn't cover them: the page sees them as `mouseup`/`auxclick` with `button` 3 and 4, and whether WebView2 also navigates on them is part of ticket 29's hand check.

**2026-11-16, from ticket 26.** What the page and the app say to each other now: one message, `ask-for-document` (`Message::AskForDocument`), makes the page ask, for another document and for a save alike; `gone` is `document-gone` with the showing it is about, and the page shows the bar only while its view shows that showing. F5 calls `requestDocument()` in `page/src/view.ts` directly. A link sends `showingInView()` with `follow_link`, and the app does nothing for a showing the window has left (`Documents::document_path_shown_as`). When Back gives the window an earlier entry's `Showing` again, these all keep working as long as the table's current showing is that entry's: a link from the entry the window just left does nothing, and a late `gone` for it shows no bar. A held notice now comes in the `render_document` answer (`notice`), not as a message. In the page's tests, `giveAnotherDocument()` returns the showing the window left, and `saveTheFile()` and `deleteTheFile(showing?)` stand in for the watch.

**2026-11-16, from ticket 28.** `Documents::give` now carries out the whole show through two ports, `Pages` and `Windows` (`app/src/documents.rs`), and the tests' `Recorder` (`app/src/documents/recorder.rs`) keeps both: `recorder.sent()` for messages and `recorder.done()` for what was done to windows (`ToWindow::Opened`, `Titled`, `BroughtToFront`). A change of document is `Documents::change`: it titles the window (`title_of`, now in `documents.rs`), then sends `AskForDocument`, and if either fails puts back the entry the window left (`put_back`) and its title, returning `ShowError::NotTaken`. Back and Forward give the window an entry in the same way, so build them on `claim`/`change` rather than beside them: the entry the window leaves comes out of `claim` (`Claimed::Changed { left, .. }`), which is where a window record would keep it in its history instead of dropping it. Every error a show gives the reader is a `ShowError` (its window has closed, didn't open, couldn't change to it, didn't come to the front). Outside the documents module, `follow` in `links.rs`, `show_dropped` in `open.rs`, `open_launch` in `window.rs` and `forward` in `menu.rs` take `&Documents`, so tests drive them with `recorded()`; another module's test gets a window's showing with `Documents::page_asks` (test-only).
