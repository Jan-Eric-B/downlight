# 20: No credentials sent for remote images

**What to build:** A remote image can't make Windows send the reader's credentials either. Ticket 06 removes images on network shares, but a remote `http(s)` image on an intranet host (`http://fileserver/logo.png`) still loads, and WebView2, like Chromium, may answer that host's NTLM or Negotiate challenge with the reader's Windows sign-in without asking. User story 28 promises that opening a document can't make Windows send credentials to a server.

Spec: [Downlight v1](../spec.md)

**Blocked by:** 06 (Raw HTML and images, safely)

**Status:** ready-for-human

- [x] Find out whether WebView2 answers an NTLM or Negotiate challenge for an image request without asking, and for which hosts (intranet zone, dotless names, any host). Record the answer and its source in this ticket.
- [x] If it does, the webview answers no such challenge for any request a document causes, for example through Chromium's `--auth-server-allowlist` browser argument on the WebView2 environment. The image doesn't load, and the page shows its alt text.
- [x] The change fits ticket 19's handling of browser arguments: a second launch whose `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` differs from the running process's still shows the document, or shows the message box as ticket 19 does.
- [ ] Remote images on ordinary internet hosts still load.
- [ ] Checked by hand on the release build against a server that asks for NTLM (for example a local IIS site with Windows authentication): no credentials are sent.
- [x] From the Comments, links to shares: following a link that leads to a network share asks the reader first, naming the host, and nothing looks at the share before a yes.
- [x] From the Comments, symlinked local images: no part of a local image's path may be a link off this computer, checked without opening the link's target, and tested with real symbolic links in a temporary folder.

## Results

Built 2026-11-16. `npm run check` passes. No contract shape, capability or content security policy changed, so `npm run fixtures` and `cargo clean -p tauri --release` aren't needed.

**The research answer.** Yes: WebView2 is Chromium's network stack, and on Windows Chromium answers an NTLM or Negotiate challenge with the reader's Windows sign-in, without asking, from any host that Windows' security zones let have it: `URLACTION_CREDENTIALS_USE`, which by default allows the Local Machine and Local Intranet zones, and the intranet zone includes dotless host names such as `http://fileserver/` and hosts that bypass the proxy. Internet hosts don't get it; they get a prompt, and a cross-origin image, as every remote image in the page is, may not show one. Setting an allowlist replaces the zones; an empty one counts as unset. Sources:

- Chromium, `net/http/url_security_manager_win.cc`: `CanUseDefaultCredentials` uses the allowlist if one is set, and otherwise asks `ProcessUrlAction(URLACTION_CREDENTIALS_USE)`, allowing `SILENT_LOGON_OK` and, for `CONDITIONAL_PROMPT`, any zone up to `URLZONE_INTRANET`.
- Chromium, `net/http/http_auth_preferences.cc`: `SetServerAllowlist` sets no allowlist for an empty string.
- Chromium, `chrome/browser/prefs/chrome_command_line_pref_store.cc`: the switch `--auth-server-allowlist` sets the pref `AuthServerAllowlist`; [chromium.org, HTTP authentication](https://www.chromium.org/developers/design-documents/http-authentication/): integrated authentication only for Negotiate and NTLM, and only for a proxy or a server in the list; without one, Windows' zones decide, by default Local Machine and Local Intranet.
- Microsoft Learn: [Edge per-site configuration, Credential release](https://learn.microsoft.com/deployedge/per-site-configuration-by-policy#credential-release) (zones decide, an allowlist stops them being consulted, dotless names are intranet); [AuthServerAllowlist](https://learn.microsoft.com/deployedge/microsoft-edge-policies/authserverallowlist) ("only enabled when Microsoft Edge receives an authentication challenge from a proxy or from a server in this list"); [AllowCrossOriginAuthPrompt](https://learn.microsoft.com/deployedge/microsoft-edge-policies/allowcrossoriginauthprompt) (third-party images can't show a prompt by default); [CreateCoreWebView2EnvironmentWithOptions](https://learn.microsoft.com/microsoft-edge/webview2/reference/win32/webview2-idl#createcorewebview2environmentwithoptions) (`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` is appended to the app's arguments; WebView2 refuses a webview whose options differ from the shared browser process's); [AdditionalBrowserArguments](https://learn.microsoft.com/microsoft-edge/webview2/reference/win32/icorewebview2environmentoptions#get_additionalbrowserarguments) (a switch given twice: the last one counts).

The docs don't say in so many words that WebView2 keeps Chromium's zone rule; it shares the code above, and the hand check below confirms it either way.

**Remote images: the browser arguments.** Every webview starts with `--disable-features=msWebOOUI,msPdfOOUI,msSmartScreenProtection --auth-server-allowlist=downlight.invalid` (`BROWSER_ARGUMENTS` and `platform::with_browser_arguments` in `app/src/platform/windows.rs`, called by `open_window` in `app/src/window.rs`). The first part is wry's own default, which setting arguments replaces. The allowlist names a host under `.invalid`, which never resolves (RFC 6761), so no server gets the sign-in on its own; a proxy's challenge is still answered, as Chromium always does. An image from an intranet host that asks for NTLM gets a 401 and shows its alt text. Fits ticket 19: every window gets the same constant, so windows in the process never disagree, and a second launch hands its documents to the running process before it builds a webview (ADR 0001), so its own `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` changes nothing. A `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` set when the first process starts is appended, and an `--auth-server-allowlist` in it would win; that is the reader's own setting. Not handled: WebView2's `BasicAuthenticationRequested` event; a cross-origin image can't prompt, so it shouldn't fire for one (the hand check shows whether a box appears).

**Links to shares: ask first.** The core decides where a path leads before anything looks at it (`core/src/files.rs`, new): `leads` gives this computer, a network share with its host, or elsewhere (a device, a volume GUID path, a loop of more than 63 links). It reads a share's host from the path's prefix without any lookup, and on this computer walks the path from its root, asking the caller's `FileSystem::link_target` about each part, so a link is read only once the folders above it are known to stay here; a link's target replaces it (relative ones against the link's folder, `..` resolved by name) and the walk starts again. `resolve_link` now takes `&impl FileSystem` (its `kind_of` and `link_target`, replacing the `kind_of` closure) and `ask_to_connect(path, host)`: a path that leads to a share is looked up only after a yes, a no or a path that leads elsewhere does nothing (`LinkAction::Nothing`), and a path on this computer asks nothing. So a link through a local symbolic link to a share asks too. A share on the host the document's own path names (`\\host\...` or `\\?\UNC\host\...`) is followed without asking, since reading the document connected there already (the owner's decision below; `is_on_share_of` in `files.rs`). Hosts are compared by name, ignoring the case of ASCII letters only, so any other spelling of the same computer (its full DNS name, its address, a name differing in a non-ASCII letter's case) counts as another host and asks. A document opened through a local symbolic link to a share counts as on this computer, so its share links ask. The app's `Disk` (`app/src/disk.rs`, new) is the real file system: `kind_of` is the old `path_kind`, moved from `links.rs`, and `link_target` uses `symlink_metadata` and `read_link`, neither of which follows the link (Rust counts a junction as a link too). The question is `platform::ask` (`app/src/platform/windows.rs`): a `MessageBoxW` owned by the window, Yes and No with No the default button, so a stray Enter answers no, on the blocking thread `follow_link` already runs on, so the main thread and other windows keep answering; other systems answer no. Its text (`connect_question` in `app/src/links.rs`): "The link goes to `<path>`, which is on a network share of the computer `<host>`. Following it connects to `<host>`, and Windows may sign in there as you. Follow the link?" The page is unchanged, and the hover bubble still shows the target without a lookup.

**Symlinked local images.** `local_image` takes the `FileSystem` too and gives None unless the image's path leads to this computer, so the image scheme answers Not Found (and the page shows the alt text) for an image that is a link to a share, or in a folder that is one, without opening the target. Rendering is unchanged: it can't see links, and the scheme checks every request.

**Glossary and spec.** A new glossary entry, Network share, and Local image now excludes a path through a symbolic link to a share. The spec's Link resolution says a path that leads to a share asks first, in place of "treated like local paths".

**Tests.**

- Core, `files.rs`: a drive path without links stays here and each folder is asked about from the root down; a share path leads to its host with no lookup (also `\\?\UNC\`); a link to a share (file, folder, verbatim UNC) leads to the share without looking there; links to this computer (absolute, verbatim, relative with `..`, root-relative) are followed; a chain of links that ends on a share; links to a device or a volume lead elsewhere; a loop leads elsewhere; an unreadable link is an error; a link to a drive without a root (`C:pics`) leads elsewhere; `.` and `..` in a link's target are resolved by name.
- Core, `links.rs`: share links ask naming the host and a no does nothing without looking there (UNC, `//`, `file://host/`, from a document on a share of another host, `\\server.example` for `\\server`); a yes follows; a share on the document's own host is followed without asking (relative, another share there, other letter case, `\\?\UNC\` against `\\`, `file://`, and through a local link); a link through a local link to a share asks naming the share's host; links on this computer ask nothing; a link through a local link to a device does nothing without asking. The existing table tests resolve with a yes.
- Core, `image.rs`: the scheme refuses an image that is, or is in a folder that is, a link to a share without looking there, and serves one linked to this computer by its own path.
- App, `disk.rs`: `kind_of` (moved), `link_target` for a plain file, a folder and a missing path, and with real symbolic links in a temporary folder: an image that is a link to a share, an image in a folder that is one, and an image linked to a file here. The links point to `\\downlight-test.invalid\share`, which never resolves, so even a broken check connects to nothing. Creating a symbolic link needs Developer Mode or the privilege; without it the three tests print `skipped: ...` on stderr and pass. On this machine they ran (no skip). A mutation that let shares through failed them.
- App, `links.rs`: a share link asks naming the host and a no leaves the window as it was and sends nothing; the question names the path and the host. The existing tests fail if anything asks.
- App, `platform/windows.rs`: the allowlist is set, not empty and names only `.invalid` hosts (an empty one would mean the zones again); wry's defaults are kept.

**Not measured.** No rendering or Find work changed. The image scheme now looks at each folder of an image's path once per request (`symlink_metadata` on a local disk), which doesn't grow with the document's size.

## Comments

**2026-11-13, from the architecture review.** Two more ways a document can make Windows send the reader's credentials, for the same promise (story 28):

- **Links to shares.** One click on a link to `\host\share\x.md`, or a folder or file there, connects to that host: the link's lookup (`path_kind` in `app/src/links.rs`) and Explorer both do. The spec chose this ("paths on network shares are treated like local paths, since they only connect when clicked"), and the hover bubble shows the target. But a downloaded README can name any host, and one click sends the reader's NTLM hash. Decide here: keep it, ask before following a link to a share, or follow only shares the document itself lives on.
- **Symlinked local images.** `is_local` (`core/src/image.rs`) checks the path's prefix, and `std::fs::read` (`app/src/image.rs`) then follows reparse points. A `logo.png` that is a symlink to `\host\share\x.png` (from a git clone with `core.symlinks`, or a tar extracted in Developer Mode) makes Windows connect. Check that no component of the path is a link to a non-local target without opening the target, since `canonicalize` would open it and so connect, then test it with a symlink in a temporary folder.

**2026-11-16, decided by the repo owner.** Links to shares: ask first. Following a link whose target is on a network share (a UNC path or `file://host/`, a document, a file or a folder) asks the reader before anything connects to that host, naming the host; only a yes follows the link. The check happens before any lookup that would touch the share (`path_kind` in `app/src/links.rs` connects too).

**2026-11-16, decided by the repo owner.** A link to a share on the host the shown document itself lives on is followed without asking, since Windows already connected there to read the document. A share on any other host still asks every time.

**2026-11-16, from the review.** Three changes, and two hand checks added.

- **Shares on the document's own host.** As the owner decided above, a link to a share on the host whose share the shown document's path names is followed without asking (`is_on_share_of` in `core/src/files.rs`, asked in `resolve_link`). `\host\` and `\?\UNC\host\` name the same host, and `file://host/` gives the first; hosts are compared ignoring ASCII case only, and any other spelling of the host still asks. The old test case of a relative link in a document on a share, which asked, now checks that a document on another host's share asks. The glossary's Network share and the spec's Link resolution say so. Built test-first.
- **No current folder in the core.** Following a link's target used `std::path::absolute`, which resolves a drive path without a root (`C:pics`) against the process's current folder on that drive. The core now resolves `.` and `..` by name alone (`without_dots`), and a target with a drive but no root leads elsewhere: it neither loads as an image nor is followed. Built test-first.
- **The image scheme's read.** `app/src/image.rs` says why the gap between the check and `std::fs::read`, which follows links, is accepted: swapping a link in between needs someone on this computer who can already write next to the document.
- **Hand checks.** Other windows keep taking input while the share question is up; links from a document on a share to its own host and to another.

Open for the owner: a document opened through a local symbolic link to a share counts as on this computer, so its links to that share still ask (the conservative side). Following the document's own links to its host would need the document's path walked on every share link.
