# 27: One page module speaks to the app

**What to build:** A refactor of the page, with no change the reader sees. Every command the page invokes and every message it listens for is named and typed in one page module, the page's counterpart to `app/src/message.rs`. Tauri's IPC is its adapter in the app, and the tests' fake app is the other. The app's tests write a sample of each answer and message as JSON, and the page's tests load them, so the two sides can't drift apart.

Spec: [Downlight v1](../spec.md)

**Blocked by:** none

**Status:** ready-for-agent

- [x] One module in `page/src/` names every command (`render_document`, `follow_link`, `open_document`, `show_document_menu`, `close_window`, `show_window`, the timing reports, `reload_document` until ticket 26 removes it) with typed arguments and answers, and every message (`document-shown`, `document-changed`, `scroll-to-heading`, `notice`, `menu-command`) with its typed payload. No other page module calls `invoke` or `listen`.
- [x] `Place` and `DocumentToShow` (`view.ts`), `Followed` (`links.ts`), the menu entries (`commands.ts`) and the timing marks (`timing.ts`) move there.
- [x] Contract samples, in the style of the rendered fixtures: a Rust test writes each answer and message the app sends as JSON under a fixtures folder, checks the committed files as `core/tests/rendered_fixtures.rs` does, and the page's tests read them through the module's types. A change to a shape fails a test on the side that didn't change.
- [x] The fake app in `page/src/test-support.ts` answers through the same module, so the tests can't call a command the app doesn't have.
- [x] No new dependency.

## Comments

**2026-11-13, from the architecture review.** Today command names are string literals in six page files, and event names in two; `listenToApp(event: string, handler: (payload: string) => void)` takes any string. `Place`, `DocumentToShow`, `Followed`, the menu entries and the timing marks are written out by hand in both languages. The Rust tests pin the JSON shapes (`handover.rs`, `links.rs`, `message.rs`), but nothing ties them to the TypeScript types. Tickets 12, 15 and 16 each add commands or messages, so this pays back at once. `answerAsTheApp` re-implements `Documents::handover`'s decision in TypeScript; keep that, but make it answer in the module's types.

**2026-11-13, done.** `page/src/app.ts` holds the `Commands` table (each command's arguments and answer), `askApp`, the `Messages` table and `listenToApp`, plus `Place`, `DocumentToShow`, `Followed`, `MenuEntry`, `FirstPaintMarks`, `ReloadMarks` and `LongTask`; `events.ts` is gone and its test is `app.test.ts`. ESLint's `no-restricted-imports` keeps `@tauri-apps/api/core`, `event` and `webviewWindow` out of every other page module but `test-support.ts`. The samples: `contract_samples` next to the types in `documents.rs`, `links.rs` and `message.rs`, written to `app/tests/fixtures/` (`render_document.json`, `follow_link.json`, `messages.json`) and checked by `app/src/contract.rs`; `npm run fixtures` writes them with the rendered fixtures. They replace the hand-pinned JSON tests in `handover.rs`, `links.rs` and `message.rs`. The page's tests drive each sample through the view, links and commands ("the app's ..." tests in `page/src/contract.test.ts`). Each `contract_samples` starts with an exhaustive match over the variants it samples, so a new variant stops the build there until it has a sample. The fake app is `fakeTheApp`, keyed by command in the module's types, with `askedOfTheApp` and a typed `tell`; `answerAsTheApp` answers `DocumentToShow` from typed arguments. The arguments the page sends are sampled too: `MenuEntry` (`menu.rs`) and `FirstPaintMarks`, `ReloadMarks` and `LongTask` (`timing.rs`) serialize in test builds only, and their `contract_samples` write `menu_entries.json` (each kind of entry, and a command with and without its shortcut) and `timing_reports.json` (first paint, a reload, a long task and a long frame). The page's tests ("the page's ..." in `contract.test.ts`) open the right-click menu, load the page with `?timing` for first paint and a reload, and stand in for `PerformanceObserver`, whose long task entries happy-dom lacks, and check the kinds and keys the page sends against the samples, not their values. A failed timing report is swallowed on the page, so these samples are what catch a drift there. The names of a command's parameters (`showing`, `target`, `newWindow`) aren't sampled: Tauri takes them from the Rust function, so no Rust type holds them to serialize, and a sample written by hand would pin nothing on the Rust side.
