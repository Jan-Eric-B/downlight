# 16: Zoom and window size

**What to build:** The reader can zoom with the usual keys and Ctrl+wheel, and the zoom level carries over to every new window. A new window opens at the size of the last window that closed, offset from the active window so windows don't stack exactly.

Spec: [Downlight v1](../spec.md)

**Blocked by:** 15 (Edit and Choose editor), 28 (The documents module carries out the whole show), 29 (The page owns every key)

**Status:** closed

- [x] Ctrl+plus, Ctrl+minus and Ctrl+wheel zoom in and out, and Ctrl+0 resets to 100%.
- [x] The zoom level is saved in the settings file and used by every new window.
- [x] A new window takes the size of the last window that closed and opens offset down and to the right of the active window, staying on screen.
- [x] Zoom in, Zoom out and Reset zoom are in the right-click menu.

## Results

Built 2026-11-16. `npm run check` passes.

- **Zoom in the app.** `app/src/zoom.rs`: the levels of Edge and Chrome from 50% to 300% (50, 67, 75, 80, 90, 100, 110, 125, 150, 175, 200, 250, 300), `Zoom`, a level always within 50 to 300% that steps (`Zoom::step`), `ZoomChange` (`in`, `out`, `reset`) and the async command `change_zoom`, which steps the level in the settings through `Documents::change_settings`. A level hand-edited into the settings file is brought within 50 to 300% when the settings load, and steps to the next level either way. A level that can't be saved holds until Downlight closes, and the page shows why ("... The zoom holds until Downlight closes.").
- **One zoom for every window.** Zoom is a setting every window shares (the glossary's Settings), so a step in one window zooms every open window too, not only new ones: `change_settings` sends every page the new snapshot. Each new window gets the level in its URL, so its first paint is at it.
- **Zoom in the page.** `page/src/zoom.ts`: `startZoom()` sets `--document-zoom` on the root from the settings, and `document.css` zooms only `article.markdown-body` with CSS `zoom`, so the title bar, the find bar, notices, the "File deleted or moved" bar and the link target keep their size (window design spec). WebView2's own zoom stays off. Zooming keeps the reading position with `keepReadingPosition(change)` in `page/src/view.ts`, built here for window design ticket 06 to use too.
- **The keys and the wheel.** In `page/src/commands.ts`, `zoomIn` (Ctrl and `+`, Ctrl+Shift and `+` as on a US layout, Ctrl and `=`), `zoomOut` (Ctrl and `-`) and `resetZoom` (Ctrl+0, also by the 0 key's place, since AZERTY types `à` there). Zoom in and out repeat while held; Reset doesn't. The number pad's `+`, `-` and `0` give the same keys. A command can name `ctrlWheel: "up" | "down"`; Ctrl+wheel never scrolls, adds up what the wheel turned, and runs the command once each 50 px, never more than once an event, so a mouse's notch is one step at any display scale and a touchpad's pinch zooms in steps.
- **The menu.** Zoom in, Zoom out and Reset zoom follow Open, between separators, showing `Ctrl+Plus`, `Ctrl+Minus` and `Ctrl+0` as Notepad does. muda takes a menu shortcut only for a key it has a code for and drops `Ctrl+Plus` without a word, so on Windows `menu.rs` now writes every shortcut into the item's text after a tab (`platform::menu_item_text`), as Windows menus write them; the other systems still hand it to Tauri's menu.
- **Size and place of a new window.** `NewWindow` (`app/src/documents/show.rs`) carries `settings`, `size` and `at` beside `title`, decided in `Documents::open` by `size_and_place` (`app/src/documents/place.rs`, with `WindowSize`, `WindowPlace`, `Point` and `Area`). The size is that of the last window that closed (`Settings::window_size`, in logical pixels), 800 by 600 until one has, never under 320 by 240, and never larger than the active window's screen. The place is 32 logical pixels (the title bar's height) down and to the right of the active window; on an axis where the window wouldn't fit on that screen, it starts again at the screen's left or top edge, as Windows cascades, and it never starts left of or above the screen. Without an active window, or with a minimized or maximized one, the system places the window, as before, at a size fitted to the main monitor's work area (`Windows::primary_work_area`). `open_window` hands the size and place to Tauri's builder in the logical pixels of the active window's monitor, so tao puts the window on that monitor at its scale.
- **The active window and the closing size.** `window::track_windows` (formerly `forget_when_destroyed`) tells the documents module of `Focused(true)` (`Documents::activated`), of `CloseRequested` (`Documents::closing`, which reads the size while the window still exists and saves it, on the main thread since closing the last window ends the process; an accepted exception to "the main thread stays free", see the review's comment below), and of `Destroyed` (`forget`, which also forgets an active window). The windows port gained `Windows::place_of(window)`: position, size and the monitor's work area in its logical pixels, None for a closed, minimized or maximized window. A minimized or maximized window that closes leaves the saved size as it was.

## Comments

**2026-11-12, from ticket 10's code quality review.** What ticket 10 left in place that this ticket builds on:

- Ticket 10 left WebView2's zoom keys (Ctrl+plus, Ctrl+minus, Ctrl+0) working on purpose: its `AcceleratorKeyPressed` handler (`leave_reload_keys_to_the_page` in `app/src/platform/windows.rs`) turns off only the reload keys. There are two ways to take zoom over:
  - Add the zoom keys to that handler.
  - Turn off all of WebView2's browser keys (`SetAreBrowserAcceleratorKeysEnabled(false)`) and remove the handler. The page must then handle the keys the handler covered, and still swallow Ctrl+F5, Shift+F5 and Ctrl+Shift+R.

  Either way, Ctrl+wheel is a separate setting (`IsZoomControlEnabled`). Check each key by hand in the release build.
- `Command` in `page/src/commands.ts` has `ctrlLetter` (a letter) and `key` (a key without modifiers). Ctrl+plus fits neither. Widen the shape for all commands rather than adding a special case for zoom; ticket 12 needs the same for Alt+Left.
- An OS hook that can't be added shouldn't fail the window (see `leave_reload_keys_to_the_page`).

**2026-11-16, from the review.** Fixed after the code review, `npm run check` passes:

- **One lock for a change and its telling.** `SettingsStore::update(change, then)` runs `then` while it still holds the settings, and `Updated` carries `before` beside `settings`, so `Documents::change_settings` compares `before.page()` with `settings.page()` and tells every page inside `then`. Of two changes at once, the pages are told last what the settings hold last, without the second mutex (`settings_changes`, gone) or an `Option` written from inside the closure. `send_to_every` is now the private `send_settings_to_every_page`.
- **Who owns the settings.** One `Arc<SettingsStore>` sits in the documents module and in Tauri's managed state. Readers such as Edit read it there (`State<Arc<SettingsStore>>`); every change goes through `Documents::change_settings`, the one caller of `update`, so a change to what the pages show always reaches every page. Chosen over a separate read-only handle, which would add a type to guard one call site; the rule is in `SettingsStore`'s and `update`'s docs rather than enforced by the compiler.
- **A window that opens while the settings change.** Its page's URL could hold the settings from before the change, and the `settings` message came before the page listened, so it was lost. The documents module now keeps, for each window whose page hasn't asked for its document yet, whether the settings changed meanwhile (`WindowTable::not_hearing`), and sends that page the current settings when it first asks (`Documents::page_hears_settings`), while the settings are held, so a later change reaches it after. The page makes that safe: `startSettings()` resolves once its `settings` listener is registered (`startListeningToApp` in `app.ts`), and `main.ts` waits for it before the document view's first request. Not put in the `render_document` answer, as notices are: an empty window's answer is null, and an answer that waits for its render can reach the page after a later `settings` message and undo it. The wait costs one IPC round trip before the first request, while the render runs ahead; not measured, since the review ran no release build.
- **A cold start on a smaller screen.** Without an active window, the size of the last window that closed is now fitted to the main monitor's work area (`Windows::primary_work_area`, Tauri's `primary_monitor`), so a size saved on a large monitor no longer opens past a smaller one's edges. The system still places the window.
- **Placement is its own feature.** `WindowSize`, `WindowPlace`, `Point`, `Area`, the default and smallest sizes, the offset and `size_and_place` are in `app/src/documents/place.rs`, its tests in `documents/tests/place.rs`; the settings' tests in `documents/tests/settings.rs`. The constants are private to the documents module.
- **`Zoom`.** The level is a `Zoom` in `zoom.rs`, brought within 50 to 300% once, when the settings load (`From<u16>`, through serde), and stepped by `Zoom::step`; `within_range` and zoom's public constants are gone. `window_size` stays as saved: a closing window gives it in the same session too, and the screen it is fitted to is known only when a window opens, so the check stays in `size_and_place`.
- **`ZoomChange` is a contract sample** (`zoom_changes.json`), and `contract.test.ts` checks that the page's menu commands ask for each change and no other.
- **The page URL** is built with `tauri::Url`'s `query_pairs_mut()` (`append_key_only` for the flags, `append_pair` for `settings`); `query_value` is gone. `page_url.json` reads the same.
- **`Documents::closing` returns nothing**, saying inside why a size that can't be saved is no one's to tell. It still writes the settings file on the main thread on `CloseRequested`: an accepted exception to "the main thread stays free", since closing the last window ends the process right after and a background task would not finish; it writes one small file, and only when the size changed.
- **The page.** `whenSettingsChange` throws before `startSettings()` rather than starting it unseen. `DEFAULT_SETTINGS` stays, for a URL the page can't read, with a comment naming `zoom.rs` and `Settings::default`. The tests use `ZOOM_VARIABLE` rather than `"--document-zoom"`.
- Tests added: `documents/tests/settings.rs` (a change reaches a page that asked at once, one before the page asks reaches it when it asks, once, and none when nothing changed), `new_window_without_an_active_window_is_made_to_fit_the_main_screen`, `update_tells_what_changed_before_another_change_starts`, `hand_edited_level_out_of_range_loads_within_it`, the zoom contract test, and a settings listener before `startSettings` failing. Tests changed: `zoom_in_reaches_every_window_and_new_ones_open_at_it` and `changing_a_setting_no_page_shows_tells_no_page` let the pages ask first, since a page that hasn't asked is now held rather than sent the change.
