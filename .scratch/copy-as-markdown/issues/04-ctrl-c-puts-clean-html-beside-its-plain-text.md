# 04: Ctrl+C puts clean HTML beside its plain text

**What to build:** Ctrl+C, and the menu's Copy, keep putting the same plain text on the clipboard, and put clean HTML beside it, so that a paste into Word or Outlook keeps the document's formatting in the target's own styles. That HTML has:

- headings, emphasis, lists, tables, quotes and code, with none of Downlight's colors, theme, copy buttons or heading anchors;
- code as plain monospace;
- alerts as quotes with their title, and footnotes as a numbered list;
- local images by their file path, web images by their URL, and images that don't load as their alt text;
- web and mail links as links, every other link as its text;
- ticks as ☑ and ☐;
- a sorted table in the order shown.

Ctrl+A then Ctrl+C copies the whole document this way. A copy in the Find box or another field is left to the webview.

Spec: [Copy as Markdown, and a clean rich copy](../spec.md)

## Results

Built on 2026-11-25.

- **Before building.** Not done: the hand check of what today's Ctrl+C pastes into Word in both themes is left for the owner.
- **Module.** New `page/src/clean-copy.ts` (`startCleanCopy(signal?)`, started in `main.ts` after `startCommands`). It listens for `copy` on the window. It does nothing (the webview copies) when the event's target or the focused element is a text field (`isEditable`, in `page/src/editable.ts`, which the shortcuts in `commands.ts` use for the same question), when nothing is selected, or when the selection doesn't reach the document view. Otherwise it sets `text/plain` and `text/html` on `clipboardData` and cancels the webview's copy. Ctrl+Shift+C (a keydown that writes through the app) and the code copy buttons (`navigator.clipboard`) raise no copy event, so the two never meet (a test of that was deleted in the review fixes: it passed for any implementation in happy-dom, so it proved nothing).
- **Design.** The selected part of the view is not cloned. A selection that runs out of the view (Ctrl+A selects the whole page) is cut to the view's edges (the shared `selectionInView()` of `view.ts`, which Copy as Markdown uses too), so the page's own parts (the empty window's button and hint) never come along. Then one walk over the original nodes, with a stack of its own rather than recursion (a document nested thousands of levels deep is copied like any other), guided by the sets of ancestors of the range's start and end, writes the HTML as a string as it goes: no `cloneContents` (which would also make the webview start loading each cloned `img`), no `innerText`, and the walk reads no layout; the only style it reads is `getComputedStyle(img).display` of an image whose source ends in `#gh-dark-mode-only` or `#gh-light-mode-only`, and the plain text, `Selection.toString()`, does lay out, as the webview's own copy does. The allowlist is one table of tag to role (`ROLES`: dropped, structure, container, inline) and the special cases in `markupOf`: structural elements are written with no attributes, except `ol start`, `th`/`td` `align`, `colspan` and `rowspan`, and an image's `width` and `height`; other elements (`div`, `span`, `section`, `details`, `picture`) are left out with their children kept; the page's own parts and what a browser never shows as text (`button`, `svg`, `script`, ...) go with their content. A selection inside one `em`, `strong`, `code`, `pre`, link and the like keeps that element around its text, as a browser's copy does, so a selection within a code block still pastes as code. A selection whose common ancestor is a list, table, table section, row, definition list or quote is wrapped in it and the containers above it (as Chromium's copy does), so two list items paste as a list and two cells as a row of a table, never as bare `li`, `td` or `tr`; the wrapping stops at the first ancestor that is not a container, so the text within one item or cell is not wrapped. The content of a closed `details`, all but its summary, is left out, as the page doesn't show it.
- **Rules.** Heading anchors (`a.anchor`) and copy buttons are dropped. Find uses the CSS Custom Highlight API (`CSS.highlights`), so there are no highlight elements in the view to remove; a test with Find's matches shown checks no `mark`, `span` or class comes out. Alerts (`div.markdown-alert`) are `blockquote`s whose first paragraph is the title the core already writes. A task item's checkbox is ☑ or ☐ by its `checked` property as the reader left it, read from the original input (a clone's checkedness isn't dependable across engines: happy-dom drops it). A local image's URL (`http://image.localhost/...`, or `image://localhost/...` off Windows) becomes `file://` plus its percent-encoded path (`file:///C:/lamps/the%20lamp.png`), without the saved-time query and the fragment, but only when that path is a drive path (`/C:/...`): any other path at the image origin (`http://image.localhost//attacker/share/x.png` would be `file:////attacker/share/x.png`, which Word or Outlook would open by connecting to that host, the glossary's Network share rule) is the image's alt text, as is one with a trailing dot after the host. The core refuses such an image too; this check stays as defense in depth. Off Windows (`image://localhost/home/...`) no path is a drive path, so those images paste as alt text, which v1 doesn't ship. A web image keeps its URL, and so does a `data:` image; one with no source (a network share's) is its alt text. An image the theme hides (`#gh-dark-mode-only` in the light theme, `#gh-light-mode-only` in the dark, by `getComputedStyle(img).display`) is left out, alt text and all. `http(s)` and `mailto` links stay links; every other link is its text. A sorted table is in the view's order because the walk is in the view's order.
- **Plain text.** `Selection.toString()` of the whole selection (not cut to the view, as the HTML is; a test says so), with its line breaks written as CRLF: the webview's default copy gives Windows its CRLF line breaks, but `setData("text/plain", ...)` writes the text as it is, so the page does (`replace(/\r?\n/g, "\r\n")`; the first version's comment claimed the webview's copy did it for us). The risk the spec names stands: Chromium's own copy text (`SelectedTextForClipboard`) differs from `toString()`, which I can't check without the webview. The differences known for the owner's hand check against the build before, on the same selections:
  - an image's alt text, which a copy emits and `toString()` doesn't (so a selection of only an image has an empty plain text);
  - content with `user-select: none`, which a copy leaves out and `toString()` may not;
  - possibly how a non-breaking space comes out, and the number of line breaks between blocks (`toString()` and a copy both walk the text but may emit a different number of newlines between paragraphs, list items and table rows).

  If they differ, the plain text is made to match; none of it is emulated here.
- **Fixture.** `core/tests/fixtures/images-and-links.md` and its HTML (written with `cargo test -p downlight-core --test rendered_fixtures -- --ignored`, the first step of `npm run fixtures`; no other fixture or the notices changed): a local image whose path has a space, a web image, an image on a network share (the core drops its source), the link kinds, and a web image in a link.
- **Tests.** `page/src/clean-copy.test.ts`, 52 tests after the review fixes below (26 before them) that raise the copy event and read `clipboardData`: the plain text (within a cell, across blocks); the cut blocks of a selection across paragraphs; no colors, classes, ids, `data-` or `aria-`; the page's own parts left out with everything selected; Find's matches shown; copy buttons and plain monospace code; heading anchors; alerts; footnotes as a numbered list without their way back; ticked and unticked items by the reader's ticks, and for a selection that reaches into the list; local, web, unloaded and linked images; kept and dropped links; a reordered table's rows in the view's order, with alignment and cell content kept; a selection within one code block and within emphasis; escaping and non-breaking spaces; and, left to the webview, a copy in the Find box, with nothing selected, and outside the view. The review fixes (below) changed and added tests.
- **Noteworthy.** Four things the ticket doesn't say. A footnote's way back (`a.footnote-backref`, "↩") is dropped, since it is a link to nowhere that would otherwise paste as a stray arrow in the numbered list. A `data:` image (the document's own, embedded) is kept as it is, since it loads without a network or a file. After the checkbox's mark, a space is added only when the text after it doesn't start with one (the core writes one), so the paste has one space, not two. The plain text of a selection that holds only an image, such as an alt-text-only selection, is the selection's `toString()` (empty), where Chromium's copy gives the alt text; the HTML still carries the image.
- **Checks.** `npm run check` fails at its first step only because Prettier also scans the stale worktree under `.claude/worktrees/`; its steps run one by one pass: Prettier (page, app, core, scripts, root files, this spec's folder), `cargo fmt`, ESLint, Clippy with `-D warnings`, `tsc`, `cargo deny`, `check:notices`, and `npm test` (418 + 3 + 130 + 29 + 1 Rust tests and 585 page tests in 30 files).
- **Left for the owner.** The hand check before building, the measurement of Ctrl+A then Ctrl+C on the 1 MB test document (see "Measuring" below), and the hand checks in the release build (Word and Outlook in both themes, the plain text against the build before, the Find box).
- **Measuring.** The timing switch already reports every page task and frame over 100 ms, so the module needs no timing line of its own. The owner starts the release build with `DOWNLIGHT_TIMING` set on the 1 MB test document (`npm run documents` writes it to `target/documents/`), presses Ctrl+A and then Ctrl+C, and reads stderr: a `timing ...` line of kind `task` or `frame` at the time of the copy means the copy took over 100 ms, with its duration; no line means it took less. For a median of several runs, repeat the copy a few times and note each line's duration (`npm run measure` doesn't copy). The walk and `Selection.toString()` (which lays out) both run inside that one task.
- **Review fixes.** From a review of the first version, each starting with a failing test:
  - A document image at the image origin with a network share's path no longer pastes as a `file:////host/share/...` URL: only a drive path becomes a `file:///` URL, anything else is the alt text (tests: the UNC route on Windows' and the off-Windows scheme, a trailing dot after the host, a path that isn't a drive path, one that leaves its drive by dots, and an encoded path with a space, `%`, `#` and a non-ASCII character whose `?modified=` query is dropped).
  - An image the theme hides, and the content of a closed `details` (all but its summary), are left out (tests for both; the hidden image is made hidden by an inline style, since happy-dom reads no `@media` from `document.css`).
  - A selection within a list, table, row, definition list or quote is wrapped in it (tests assert the full HTML for two list items, two items of an ordered list with its `start`, two rows, two cells of one row, a header and a row, two paragraphs of a quote, a term and its description, and the nested list; and that the text within one item isn't wrapped).
  - The plain text has CRLF line breaks (tests; the existing code block test now expects them).
  - `selectionInView()` replaces the module's own clipping; `ROLES` replaces `KEPT` and `AROUND_TEXT`; `tagged` is `plainTags` and `tagsWithAttributes`; `Markup` is a union of tags and text (an alt text or a checkbox's mark is `text`, not a tag whose `open` is text); the walk uses a stack of its own (test: 5,000 levels of nested quotes, which a recursive version overflowed on before the stack was used); the header comment no longer claims "no layout".
  - `isEditable` moved to `page/src/editable.ts`, used by `commands.ts` and `clean-copy.ts`.
  - Tests: the `toBe(selection.toString())` expectations are literals; the test that Ctrl+Shift+C and the copy buttons raise no copy event is deleted (it passed for any implementation in happy-dom); added `ol start`, `colspan` and `rowspan`, a `data:` image, a quote and `<` in a link target and an alt text, `javascript:` and `file:` links as their text, and that the plain text covers the whole selection while the HTML is cut at the view. They build their HTML in the test rather than extend `core/tests/fixtures/images-and-links.md`, since the core sanitizes or refuses some of those cases away (the image at the image origin, the `javascript:` link), and the fixtures are the core's real output; no fixture changed.
