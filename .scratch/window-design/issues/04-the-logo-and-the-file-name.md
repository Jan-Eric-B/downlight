# 04: The logo and the file name in the title bar

**What to build:** The title bar's left side: the amber logo, which shows "Downlight" on hover and opens the window menu on a click; the document's file name, which shows its full path on hover and reveals the file in Explorer on a click; and the zoom level when it isn't 100%, which resets on a click.

Spec: [Window design](../spec.md)

**Blocked by:** 01 (Spike: the page draws the title bar), 02 (The amber icon and the accent scale), v1 [16](../../downlight-v1/issues/16-zoom-and-window-size.md) (Zoom and window size)

**Status:** closed

- [x] The logo is the icon's SVG inlined into the page (the content security policy has no `'self'` in `img-src`). Its tooltip is "Downlight", and a click opens the window menu, as Alt+Space does. (Built, and tested up to the app's `show_window_menu`; the menu itself is hand check 1.)
- [x] The file name shows the shown document's file name and follows it on links, Back, Forward, Open and drops. The empty window shows only the logo (changed by ticket 14: it shows "Downlight" in the file name's place). (Back and Forward don't exist yet, v1 ticket 12; they will show their documents the same way, so the name follows them with no change here.)
- [x] Hovering the name shows the full path. A click reveals the file in Explorer through the app's `reveal_file`; a missing file shows a notice instead.
- [x] The zoom level (`125%`) shows next to the name only when it isn't 100%, and a click resets it. (Built and tested; its look is hand check 7.)
- [x] A long file name is cut with an ellipsis before it pushes the buttons. (Built; hand check 3.)
- [x] The window's OS title stays "README.md - docs - Downlight" (v1 story 10). (Unchanged: `title_of` in `app/src/window.rs` now takes its names from `file_name_shown`, and its tests pass unchanged.)
- [x] The logo, name and zoom level are not part of the drag region; the rest of the left side is. (Built for the logo, the name and the zoom level; hand checks 4 and 7.)
- [x] Page tests: the name and its tooltip after a show and after a link; the reveal request on a click; the zoom level hidden at 100%, shown otherwise, and reset on a click.

## Comments

**2026-11-13, from the grilling.** The reveal is a single click, not a double-click: a double-click on a title bar maximizes on Windows.

**2026-11-16, built without the zoom level; the hand checks are left.** The zoom level waits for v1 ticket 16, which isn't built, so there is no zoom to show yet: its box, and the zoom part of the page tests' box, stay open for whoever builds ticket 16. What was built, and what it decided:

- **The file comes with the render.** The page learns the shown document's file from `render_document`'s answer, which now carries `file: { name, path }` (`DocumentFile` in `app/src/documents.rs`) with every show, reload and unreadable file; the contract samples have it, regenerated with `npm run fixtures`. The app works out the name, so the page never parses a path. The document view hands the file to its `whenDocumentShown` listeners as a third argument, and the title bar is one of them, so the name follows every way a window gets a document (a link, Open, a drop, a launch's second window, and later Back and Forward) with nothing of its own to keep in step. A document whose file can't be read still shows its name, so the reader can see which file it is and reveal its folder. The empty window hides the name and keeps the logo.
- **The reveal is a new command, `reveal_document`, that takes no arguments.** It reveals the calling window's document as the app's own state knows it (`Documents::document_path`, as `follow_link` does), so the page can't have any other file revealed and there is nothing to validate. It calls the existing `platform::reveal_file` on a blocking thread, as `follow_link` does, since a network share connects only then. It looks at the file first: a missing file fails with "Can't find C:\...\README.md, so it can't be shown in its folder.", which the page shows as a notice, rather than Windows' reason-less failure. The command is in `app/src/title_bar.rs`, with `cargo test`s for the missing file and the failure message; a reveal that works opens Explorer, so it is a hand check. If the window was just given another document and the page hasn't shown it yet, the click reveals the new one; that window is a few milliseconds wide and was left alone.
- **The window menu** is a new command, `show_window_menu`, which on Windows posts `WM_SYSCOMMAND` with `SC_KEYMENU` and a space, exactly what Alt+Space makes Windows send, so the menu is Windows' own, at the place Alt+Space puts it, with its entries enabled for the window's state (`app/src/platform/windows/title_bar.rs`). Posted, not sent, so the command doesn't wait while the reader is in the menu. Opening Windows' menu by hand with `TrackPopupMenu` would have let it open right under the logo, but then the entries' states are ours to keep, as Windows Terminal does; if hand check 1 shows the menu in an odd place, that is the fallback. Other systems keep their native title bar, so their `show_window_menu` is a plain fallback that fails as unsupported.
- **The logo** is `app/icons/icon.svg` imported raw and inlined, with its prefixed gradient id from ticket 02; its comment comes along (about 600 bytes). It is a button with the tooltip and accessible name "Downlight", at 16 px. It has no hover look, as Windows' own window icon has none. It stays amber in high contrast too (`forced-color-adjust: none`), as the spec keeps it amber always.
- **The name** is a button holding a span, so the span can be cut with an ellipsis: the name shrinks first (`flex: 0 1 auto`, `min-width: 0`) and the window buttons never do. It uses Windows 11's caption font (12 px Segoe UI Variable), dims with the bar when the window isn't active, and has a light hover background so it reads as clickable. In high contrast its hover is `Highlight`, as the window buttons'.
- **Focus and dragging:** the logo and the name are `app-region: no-drag`, never take the focus (`tabindex="-1"`, and the bar's `mousedown` is prevented already), as the window buttons. Everything else on the bar between the name and the buttons stays the drag region.
- **No new glossary term:** the window menu is Windows' own word, and the document's file is the glossary's Document.

**2026-11-16, review fixes.** Only the look before the reveal says a file is missing now: the reveal's own not-found failure (Windows has no shell item for the path, or `ERROR_BAD_NETPATH`) also comes from an offline share, where the file may well exist, so it shows as "Can't show ... in its folder: ..." with Windows' reason instead of "Can't find ...". A test reproduces it through `reveal_with`, which takes the OS's reveal; the null shell item's error has a message now, which links' reveal shows too. The name the title bar shows and the one in the window's OS title come from one function, `file_name_shown` in `app/src/documents.rs`, so the two can't drift; `title_of` uses it for the file and its folder, with its tests unchanged. Its drive-root fallback stays, so the name is never blank, and its test says it only guards that, as no document is a drive root.

**2026-11-16, review fixes in the page.** The `whenDocumentShown` listeners now take one object, `{ view, reason, file }`, rather than three arguments, so the title bar takes only the file. The logo's and the name's clicks show a failure with `showingWhy`, now in `page/src/notice.ts` and shared with the commands, Open and links; `commands.ts` says the logo and the name aren't commands, as their name and tooltip come from the window and its document. The title bar's styles moved from `document.css` to `page/src/title-bar.css`, loaded after it from `main.ts`: the logo, the name and the window buttons share one `bar-item` class for their reset (no border or background, the bar's color, not a drag region), and the hover and pressed fills are `--title-bar-hover` and `--title-bar-pressed` on `.title-bar`, with the look unchanged. The page tests hand the title bar the file's name and path as the app does, rather than cutting the name from the path.

**2026-11-17, the zoom level built; its hand check is left.** v1 ticket 16 is built, so the zoom level is too:

- **It is the Reset zoom command.** `createZoomLevel` in `page/src/title-bar.ts` makes it with `commandButton("resetZoom", "")` and writes the level as its text, so a click runs the same command as Ctrl+0 and the right-click menu's Reset zoom, and its tooltip is "Reset zoom (Ctrl+0)". Its accessible name is "125%, Reset zoom": WCAG's label in name asks that the text a reader sees is part of the name. `commands.ts`'s comment now says so beside the logo and the name, which stay no commands.
- **It follows the settings snapshot** (ticket 12): the title bar has a `whenSettingsChange` listener, so the level shows from the page's URL when a zoomed window opens, and follows every zoom from any window. It hides at 100%, and in the empty window, which shows only the logo (box 2) and has no document to zoom.
- **It sits with the logo and the name**: right of the name, a `bar-item` and so not part of the drag region, never in the focus (`tabindex="-1"`; Ctrl+0 is the keyboard's way), in the name's caption font and hover fill, at 70% opacity so the name stays what the eye finds first, full opacity under the pointer and in high contrast.
- **Tests** (written first, failing): hidden at 100%, shown and following each change, shown at once in a window that opens zoomed, its name and tooltip, a click asks `change_zoom` with `reset`, hidden in the empty window, never in the focus. The contract tests drive the sampled `settings` message (125%) into it. The title bar's tests now start the settings first, as `main.ts` does, since the bar listens to them.
