# 06: Full width

**What to build:** **Full width** lets the document fill the window instead of GitHub's reading width. A toggle button in the title bar, Ctrl+Alt+W and a right-click menu entry switch it, and the choice is kept in the settings for every window.

Spec: [Window design](../spec.md)

**Blocked by:** 03 (The accent color in the page), 05 (Open and Edit buttons, and the separators), 12 (Settings reach every page)

**Status:** ready-for-human

- [x] The button, Ctrl+Alt+W and the menu entry run one command, and the button shows in the accent color while Full width is on. (Built and tested up to `aria-pressed`; the color is hand check 2.)
- [x] Switching it keeps the reading position. (Tested; hand check 3.)
- [x] The choice is saved in the settings file and applies to every open window and every new one.
- [x] Page tests: the command switches the view's width and the button's state; a new window starts with the saved choice.
- [x] App tests: the settings keep Full width across a restart and default to off.

## Comments

**2026-11-16, decided after the review of tickets 03 and 04.** A switched-on title bar button shows its glyph in `--accent-emphasis` (Dark 1 in light, Light 1 in dark, at least 3:1 as WCAG asks of icons) on the bar's normal hover background, with no accent fill, so the spec's shade table and the five roles stay as they are. When the window isn't active, the switched-on glyph dims with the bar, as Windows dims its own caption.

**2026-11-16, from the design review of v1 tickets 12 to 15.** Full width arrives through the settings snapshot (ticket 12, now a blocker). "Switching keeps the reading position" and v1 ticket 16's CSS zoom both mean "read the line, change the layout, land again": export one `keepReadingPosition(change)` from `page/src/view.ts` that does it with `reading-position.ts`, and let Find hear it as it hears a reload, rather than building it twice.

**2026-11-16, from v1 ticket 16 (Zoom and window size).** `keepReadingPosition(change)` is built in `page/src/view.ts`: it reads the reading position, runs `change`, and puts the view back at it, and of two changes in quick succession only the later one lands. It doesn't tell Find or the `whenDocumentShown` listeners anything, since the view's content stays as it was and Find's matches are ranges in it that stay valid; if Full width's toggle needs Find to hear it (for instance once the overview ruler draws match positions), that is this ticket's call. The settings snapshot of ticket 12 is built too (see its Comments), so Full width is a field of `PageSettings` and a `whenSettingsChange` listener.

**2026-11-17, built; the hand checks are left.** What was built, and what it decided:

- **A setting through the snapshot.** `Settings` and `PageSettings` (`app/src/settings.rs`) have `full_width`, `fullWidth` to the page, off by default and for a settings file without it. It reaches the page as every setting does: in its URL when the window opens, and in the `settings` message to every window when it changes. The contract samples have it on (`page_url.json`, `messages.json`, regenerated with `npm run fixtures`), so a page that ignored it fails its test. The page's `isPageSettings` now asks for `fullWidth` too, so a URL with a snapshot from before it gives the defaults; the app always writes the whole snapshot.
- **The app switches it, the page doesn't set it.** The new command `switch_full_width` (`app/src/full_width.rs`) takes nothing and flips the setting through `Documents::change_settings`, as `change_zoom` steps the zoom, so two windows that switch it at once each switch it and every page then shows what the settings hold, rather than each page sending the value it last saw. A choice that can't be saved holds until Downlight closes and says so ("... Full width holds until Downlight closes.").
- **The page** has `page/src/full-width.ts`: `startFullWidth()` (in `main.ts` after `startZoom`, before the document view, so the first paint is at the right width) puts `full-width` on the page's root, inside `keepReadingPosition` from `view.ts`, only when the value changes; `document.css` drops the article's `max-width` under it and keeps its 32 px padding. Only the document view widens: the empty window's Open file and the notices keep their widths. Find hears nothing, as for zoom: the content stays, and its matches are ranges in it; once the overview ruler draws match positions it will need to hear a layout change, which is that ticket's call.
- **The command** `fullWidth` in `page/src/commands.ts`: "Full width", Ctrl+Alt+W, `pressed: isFullWidth`. `isFullWidth` reads the settings snapshot itself (the new `settingsNow()` in `page/src/settings.ts`), not a value a listener keeps, so the title bar's refresh on a settings change never reads it before Full width's own listener has run. Its button is in the bar's second group with the 16 px regular `arrow_bidirectional_left_right` glyph (Fluent has `auto_fit_width` only at 20 px). Its menu entry sits after Reset zoom in a group of its own, where Keep on top joins it; Settings goes last (ticket 08).
- **A check mark in the right-click menu.** A menu entry of a command with `pressed` carries `checked` (`MenuEntry::Command` in `app/src/menu.rs`), which the app shows as Tauri's `CheckMenuItem`; entries without it stay plain `MenuItem`s. New contract sample `switchedOnCommand` in `menu_entries.json`.
- **The switched-on look** is the decided one, styled once for every toggle in `page/src/title-bar.css`: `.command-button[aria-pressed="true"]` has its glyph in `--accent-emphasis` with no fill of its own, and in an inactive window the glyph dims (opacity 0.4) with the bar. A new row in `accent.test.ts`'s use table. In high contrast the role is `Highlight`.
- **AltGr isn't Ctrl+Alt+W.** Windows reports AltGr as Ctrl+Alt, and the command table matches a letter by its key's place on layouts whose key isn't a Latin letter (for Cyrillic). So on Czech, AltGr+W, which types `|`, matched Ctrl+Alt+W, and typing `|` in Find's box would have switched Full width. `pressesKey` now never takes a key that types one character other than a letter as a letter's shortcut; Cyrillic Ctrl+Alt+W still works. Tested both ways.
- **A test changed:** `commands.test.ts`'s "the window stays open on Ctrl+W with Alt held too" asserted that Ctrl+Alt+W asks the app nothing, which this ticket's shortcut contradicts; it now asserts the window isn't closed.
- **Tests** (written first, failing): `page/src/full-width.test.ts` (the button, Ctrl+Alt+W and the menu entry each switch it; Cyrillic and AltGr; the tooltip; off by default; a settings message widens the view and presses the button, and back; a new window starts with the choice in its URL; the menu's check mark; a failed save shows why; switching keeps the block at the top of the view, and a message that leaves it as it was doesn't move the view); contract tests for the URL and the message; `app/src/settings.rs` (`full_width_defaults_to_off`, `saved_full_width_loads_after_a_restart`); `app/src/full_width.rs` (switching reaches every window and new ones open with it, switching again turns it off, an unsaved switch says why).

**2026-11-17, review fixes.** The AltGr guard above still let a key that types a Latin letter outside a-z through to the match by the key's place: on US-International, AltGr+W types `å` and AltGr+T `þ`, which Windows reports as Ctrl+Alt with `code` `KeyW` and `KeyT`, so typing them in Find's box switched Full width for every window (and Keep on top) and lost the letter; a dead key on AltGr+W did the same. `pressesKey` in `page/src/commands.ts` now goes by the key's place only when the key types one letter of a script other than Latin (Cyrillic and the like), and `typesOtherThanALetter` is gone.
