# 13: A window sometimes shows a white backdrop behind a dark page

**What to build:** Every window shows its document legibly from its first frame: the backdrop behind the page always matches the page's theme, also when several windows open at once. Today a window can come up with white text on a white background until something makes Windows draw it again.

Spec: [Window design](../spec.md)

**Blocked by:** none

**Status:** closed

## Comments

**2026-11-17, seen during the hand checks of tickets 04 to 07.** The release build (commit f325a45) was started from `target/hand-checks/` with three documents at once: `downlight.exe 00-start-here.md title-bar-and-zoom.md full-width.md`. The window of the first document, `00-start-here.md`, showed white text on a white background; the other two looked normal. A little later it was fine without the reader knowing what changed it. It hasn't been reproduced yet.

What the symptom says: white text means the page took the dark theme and drew no background of its own, as it does when the app says the window has a backdrop (`backdrop` flag, `page/src/backdrop.ts`). The white came from behind the page, so the window's Mica was light, or not drawn yet, while the page was dark. Then something (focus, activation, a resize or a theme message) made Windows draw it right.

Where to look:

- `open_window` in `app/src/window.rs` builds every window hidden (`.visible(false)`, shown once the page has drawn its first frame by `show_window`) and transparent with Mica (`platform::with_backdrop` in `app/src/platform/windows.rs`, `Effect::Mica`, which "follows the system's light or dark mode"). Whether Mica on a window built hidden takes the system's dark mode before it is first shown, and whether that differs for the first window of a launch, is unchecked.
- The first window of a launch opens from `main.rs`'s setup, before the event loop runs; the others follow it. A race between the windows, or between a window's dark-mode attribute and its first show, fits "only the first of several".
- The page's theme comes from `prefers-color-scheme` in the webview, the backdrop's from the window. They are decided in two places, so nothing keeps them in step today; ticket 08's Theme setting will make the app decide both (see 08's comment on `Settings::window_look()`), which may be the natural place for the fix.

Questions for the reader if it comes back: was Windows in dark mode, what made it right (clicking into the window, switching windows, a resize, nothing), and is it always the first window of a launch?

**2026-11-17, cause and fix.** Not reproduced: no agent may launch the app, so the cause comes from reading Tauri 2.12.5, tauri-runtime-wry 2.12.3, tao 0.37.2, wry 0.57.2, window-vibrancy 0.8.1 and webview2-com 0.39.1 at the versions in `Cargo.lock`, Microsoft's docs and Tauri's own reports. The mechanism below is each step read in the source; that the reported launch went through it is the most likely explanation, not an observed one.

The white was never Mica, and the backdrop and the page's theme don't disagree. Both come from one reading: tao reads light or dark from Windows (`AppsUseLightTheme`) as it creates each window and sets `DWMWA_USE_IMMERSIVE_DARK_MODE` from it, which Mica's tint follows (`Effect::Mica` calls `window_vibrancy::apply_mica(hwnd, None)`, which sets only `DWMWA_SYSTEMBACKDROP_TYPE`), and tauri-runtime-wry gives the same theme to the webview as WebView2's `PreferredColorScheme`, which is the page's `prefers-color-scheme`; on a later theme change tao's `ThemeChanged` updates both again. The white is the window's redirection surface, the GDI surface every window has unless created with `WS_EX_NOREDIRECTIONBITMAP`:

1. `open_window` builds every window transparent (`platform::with_backdrop`). tao makes a transparent window see-through with `DwmEnableBlurBehindWindow`, so its surface shows wherever the page draws nothing, as on a page on a backdrop. The surface is white until something paints it clear: Tauri's `no_redirection_bitmap` exists to avoid exactly that "initial white redirection bitmap frame" of transparent windows (tauri-apps/tauri PR 15410, issues 14831, 15490 and 14515). Tauri paints it clear (`draw_surface`, filled with 0) when the window is built, while it is still hidden, and again on each `RedrawRequested`, that is on each `WM_PAINT` that reaches tao's event loop; the white those reports show, on Tauri versions that already did both, says the first paint doesn't hold for a window built hidden.
2. The launch's windows are built one after another in `main.rs`'s `setup`, which Tauri runs inside the event loop's handler (`RunEvent::Ready`). Building a webview waits for WebView2 with `webview2_com::wait_with_pump`, a nested message loop, so while window 2 and 3 are built the main thread still dispatches WebView2's callbacks, the IPC of window 1's page among them (wry calls the `ipc` scheme's handler right in `WebResourceRequested`, and Tauri runs a sync command such as `show_window` there).
3. Window 1's page, whose webview came first, can draw its first frame and ask `show_window` while `setup` is still building the others. The window is shown, but tao's `WM_PAINT` handler, re-entered while its event handler is busy (`should_buffer()`), only asks for the paint again (`RDW_INTERNALPAINT`) and sends no `RedrawRequested`, so nothing paints the surface clear until `setup` returns. Until then the dark page, with its white text and no background of its own, sits on the white surface: white on white. Once the last window is built, the held paint goes through, Tauri clears the surface and Mica shows, which is the "a little later it was fine without the reader doing anything".
4. Only the first window: windows 2 and 3 can't ask to be shown before `setup` is done with them, and they are shown with tao's event loop free, which paints them at once. Whether it happens depends on whether page 1 is ready before window 3's webview is, a race of a few hundred milliseconds, hence "sometimes". A second launch's documents open from the single-instance handler, where the same can happen for a shorter time, while one window's webview is built.

The test: only a real window shows it. The white is DWM composing a window's unpainted GDI surface, and whether it shows depends on when WebView2 dispatches page 1's `show_window` within another window's build; no seam of Downlight's own sees either. What `open_window` asks of the `Windows` port is the same in a launch that shows the white and one that doesn't, and Tauri's mock runtime draws nothing, so a test there would pass before the fix too. The check by hand below is the reproduction.

The fix: `platform::with_backdrop` (`app/src/platform/windows.rs`) builds the window with `no_redirection_bitmap(true)`. A window with `WS_EX_NOREDIRECTIONBITMAP` "does not render to a redirection surface" (Microsoft's Extended Window Styles), so there is no surface to be white: the window shows only the webview's own composition and Mica, from its first frame, whenever its paint comes. tao then skips its blur-behind call, which only made that surface see-through. Windows 10, which has no backdrop, keeps its solid, opaque window. The flag the page reads (`backdrop`) and ticket 08's plan are unchanged: the app still decides the backdrop, and since tao's one theme already feeds Mica and the page, ticket 08's Theme can set it with `Window::set_theme`, which goes through tao's `ThemeChanged` to the webview's `PreferredColorScheme` too. That scheme belongs to the WebView2 profile, which every window shares, so a theme is one for all windows, as the setting is.

**2026-11-17, from the reviews.** The thermo-nuclear and design reviews approved the fix. Mica behind the page now depends on DWM drawing the system backdrop under a window with no redirection surface: tao skips `DwmEnableBlurBehindWindow` when `no_redirection_bitmap` is set, and nothing calls `DwmExtendFrameIntoClientArea`. Microsoft's doc of `DWMWA_SYSTEMBACKDROP_TYPE` says the backdrop is drawn behind the whole window, and Tauri documents the option for this case, but only the hand check confirms it.

- On Windows 11 builds 22000 to 22620, window-vibrancy sets the undocumented `DWMWA_MICA_EFFECT` instead of `DWMWA_SYSTEMBACKDROP_TYPE`, a path the dev machine (build 26200) doesn't take. The hand check above now has a launch on Windows 11 21H2, or a note that it is unchecked.
- The doc comment on `with_backdrop` is corrected: tao follows later theme changes too, and the cause is told as the likely reason, not as observed.
