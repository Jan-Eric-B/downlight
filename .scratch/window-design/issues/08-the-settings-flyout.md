# 08: The settings flyout

**What to build:** The Settings button (and Ctrl+,) opens a flyout under it with Theme, Backdrop, Accent color and Edit with. A change applies at once to every open window and is kept in the settings. "Choose editor..." leaves the right-click menu, and Settings joins it, last.

Spec: [Window design](../spec.md)

**Blocked by:** 05 (Open and Edit buttons, and the separators), v1 [15](../../downlight-v1/issues/15-edit-and-choose-editor.md) (Edit and Choose editor), 12 (Settings reach every page)

**Status:** ready-for-agent

- [ ] The flyout is drawn by the page under the gear, above the document, and doesn't cover the whole window.
- [ ] Esc, a click outside and the gear again close it. While it is open, Tab moves through its controls and the focus stays inside; on closing, the focus returns to the gear.
- [ ] **Theme:** System (default), Light, Dark. The app sets the theme, so Mica's tint, the title bar and the page's `prefers-color-scheme` follow together. Tauri's `set_theme` also sets WebView2's preferred color scheme, for every window at once (see the comment from the reviews of tickets 12 and 13).
- [ ] **Backdrop:** Mica (default), Mica Alt (`Effect::Tabbed`), Acrylic, None (solid). It changes live. On Windows 10 it is disabled, with the reason as its tooltip.
- [ ] A window is built for a backdrop whenever the OS can show one, whatever the reader's Backdrop: `platform::with_backdrop(builder, backdrop)` makes it transparent with no redirection surface and sets its first effect from the choice, and does nothing where there is no backdrop (the `if` in `open_window` goes). `platform::set_backdrop(window, backdrop)` changes the effect live. On Windows 11, None clears the effect and the page draws its solid background.
- [ ] The window look (Theme and Backdrop, `Settings::window_look()`) crosses the `Windows` port: `NewWindow` gains `look` next to `settings`, and `Windows::set_look(window, &look)` changes it, with no failure for a closed window or one not built yet, and never waiting for the main thread. When `page_hears_settings` finds that a page missed a change, it calls `set_look` for that window too.
- [ ] `page/src/backdrop.ts` follows the settings (`whenSettingsChange`, or the `whenSettingChanges` helper below) instead of reading `pageFlags().backdropSupported` once: the URL flag only says the OS can show a backdrop (renamed from `backdrop` in ticket 12's review), and the page draws no background when it can and the reader's Backdrop isn't None. Moved here from ticket 12.
- [ ] **Accent color:** Amber only, until ticket 09 adds Windows' accent color.
- [ ] **Edit with:** "Default (name of the `.txt` program)", the chosen editor if any, and "Choose..." which opens v1 ticket 15's file dialog.
- [ ] Each change is saved in the settings file and sent to every open window.
- [ ] Page tests: opening and closing (Esc, outside, gear), the focus, the change the page sends for each control, and a `settings` message with Backdrop None bringing back the solid background.
- [ ] App tests: theme and backdrop kept across a restart, defaults when missing, a broken value loads its field's default and keeps the others, a new window opens with the reader's theme and backdrop, and a change of look reaches every window.
- [ ] Checked by hand: every theme with every backdrop, light and dark Windows, transparency effects off, high contrast, and Backdrop None, then resize and maximize: no black or see-through edges.

## Comments

**2026-11-16, from the review of tickets 03 and 04.** The theme has to reach WebView2's preferred color scheme, not only CSS's `color-scheme`: github-markdown-css switches light and dark on `@media (prefers-color-scheme)`, while the page's own colors and the accent roles in `page/src/accent.css` use `light-dark()`, which follows `color-scheme`. Setting only `color-scheme` on `:root` would recolor the page's parts but leave GitHub's colors in the other theme.

**2026-11-16, from v1 ticket 15.** What the settings file and Edit leave for this ticket:

- The store is `SettingsStore` in `app/src/settings.rs`, managed state loaded in `setup` before any window opens. Add each value as a field of `Settings` (the struct has `#[serde(default)]`, camelCase), with an accessor like `editor()`, and change it with `update(|settings| ...)`, which saves the whole file and keeps a change it couldn't save for the session (`SettingsError::Write`).
- "A broken value loads the default" is not what the file does now: any value of the wrong type fails the whole file, which is kept as `settings.json.bad`, and every value takes its default. Giving each field its own fallback (for example a `deserialize_with` that turns an error into the default) is this ticket's; a file that isn't JSON at all should still go to `.bad`.
- Edit with: "Choose..." is the `chooseEditor` command (`page/src/edit.ts`, the app's `choose_editor`), which already refuses Downlight and anything but an `.exe`. "Default" needs a new command that clears the editor (`update(|settings| settings.editor = None)`). The text file program's file comes from `platform::text_file_program()`, which is None when the system names none, as for some packaged programs (Windows 11's Notepad may be one); a friendly name for "Default (name)" needs `AssocQueryStringW` with `ASSOCSTR_FRIENDLYAPPNAME` in the Windows module.
- When Choose editor... leaves the right-click menu, remove `"chooseEditor"` from `menu` in `commands.ts` and keep the command, which the flyout runs.

**2026-11-16, from the design review of v1 tickets 12 to 15.** Ticket 12 (Settings reach every page) is now a blocker: it replaces the per-field accessors suggested above with one snapshot (`SettingsStore::get`, `update` returning the new snapshot) and sends it to every window, and `backdrop.ts` already listens for changes there.

**2026-11-17, from ticket 06's review fixes.** A shared setting no longer costs a Tauri command of its own. Adding one (Theme, Backdrop, Accent color) costs a field of `Settings` and its line in `Settings::page()` (`app/src/settings.rs`) if the page shows it, a `SettingChange` variant with its `apply` arm, its notice name and its sample in `contract_samples` (`app/src/settings/change.rs`, whose exhaustive match stops the build until it has one), and on the page its field in `PageSettings`, `DEFAULT_SETTINGS` and the `isPageSettings` guard and its variant of `SettingChange` (`page/src/app.ts`); the flyout's controls call `changeSetting` in `page/src/settings.ts`. `npm run fixtures` writes the new samples. The field also takes the fallback helper, so that a broken value loads its default (added from the reviews of tickets 12 and 13, below). A value the reader picks is a set (`{ setting: "theme", theme: "dark" }`), not a switch like Full width's. Clearing the editor ("Default") could be a variant too, though Choose editor... stays its own command, since it opens a dialog.

**2026-11-17, from the review of 04 to 07.** Two design recommendations deferred to this ticket, and a note on the gear button, none of them built yet:

- **A helper for settings the page shows but that don't lay out the document.** `whenSettingChanges(key, listener)` in `page/src/settings.ts`, which runs `listener` at once and then only when `settings[key]` changed, for Backdrop and Accent color, so each of them doesn't keep its own "skip if unchanged" copy. Settings that lay out the document view (zoom, Full width) don't use it: they go through the one layout follower, `startLayout` in `page/src/layout.ts`, which changes them together in one `keepReadingPosition` so the document wraps anew once.
- **Settings that act on the window, not the page** (Theme, Backdrop): add `Settings::window_look()` beside `page()` in `app/src/settings.rs`, and in `Documents::change_settings`' update callback apply it to every window through the `Windows` port when it changed. Keep "the OS can show a backdrop" as a URL flag (since renamed `backdropSupported`) and put the reader's choice in the page settings; the page draws no background when the backdrop is supported and the choice isn't none.
- **The gear button is not a `pressed` toggle.** Its open state is `aria-expanded`, owned by the flyout module, and doesn't go through the command table's refresh (`refreshCommands` in `page/src/commands.ts`), which would make the command table import the flyout and the flyout the command table.

**2026-11-17, from ticket 12's closing pass.** Ticket 12 is closed, but `backdrop.ts` does not listen for changes yet, whatever the 2026-11-16 comment above says: it still reads `pageFlags().backdrop` once. Until this ticket adds the reader's Backdrop to `PageSettings`, a listener would have nothing to read, so the move is this ticket's (the new box under Backdrop). A page test for it: a `settings` message with Backdrop None puts the solid background back without reloading the page. Ticket 13 (the white backdrop behind a dark page) may change what the flag tells the page first; check its findings before renaming the flag. (Since checked and renamed: see the next comment.)

**2026-11-17, from the reviews of tickets 12 and 13.** Ticket 13's fix builds a window with Mica with no redirection surface (`.no_redirection_bitmap(true)` in `platform::with_backdrop`), and ticket 12's review renamed the app's URL flags: `WindowLook` in `app/src/window.rs` is now `PageFlags`, which carries `timing` too, and the `backdrop` flag is `backdropSupported` (`backdrop_supported` in Rust). `change_settings`, `send_settings_to_every_page` and `page_hears_settings` moved from `app/src/documents.rs` to `app/src/documents/settings.rs`. What that means here (the boxes above now say it):

- **Built with the window, or changed live.** `transparent(true)` and `no_redirection_bitmap(true)` can only be set when the window is built; the effect (`Window::set_effects`) can change at any time. So the half set at building depends only on whether the OS can show a backdrop, never on the reader's choice: on Windows 11 the reader's None means "effect cleared, the page draws its solid background", not an opaque window as on Windows 10. Proposed shape: `platform::with_backdrop(builder, backdrop)` (transparent, no redirection surface, first effect from the choice; it does nothing where there is no backdrop, so the `if` in `open_window` goes), `platform::set_backdrop(window, backdrop)` for live changes, and `has_backdrop()` stays the support flag, also for disabling the control on Windows 10. A window with no redirection surface shows nothing where the webview hasn't painted, hence the new line in the hand check: Backdrop None, then resize and maximize, with no black or see-through edges.
- **The window look crosses the `Windows` port.** `NewWindow` (`app/src/documents/show.rs`) gains `look`, from `Settings::window_look()` (Theme and Backdrop), next to `settings`. `Windows` gains `set_look(window, &look)`, for which a closed window or one not built yet is no failure, as for `set_title`. The recorder records it (`ToWindow::Looked(look)`), with the tests "a new window opens with the reader's theme and backdrop" and "a change of look reaches every window". A race: the adapter skips a window still being built when the look changes, so when `page_hears_settings` finds that a page missed a change, it calls `set_look` for that window too.
- **The locks.** `change_settings` runs its callback under the settings lock, and `Documents::closing` takes that lock on the main thread; the settings lock is taken before the window table's, never under it. Tauri's setters (`set_theme`, `set_effects`) only post to the event loop, so they are safe there; a getter waits for the main thread and would deadlock against a closing window. Say on `Windows::set_look` that it must not wait for the main thread.
- **The theme in the adapter.** `AppHandle::set_theme` keeps a preferred theme in tao's event loop, which windows built later take too, and sends every window `ThemeChanged`, which also sets each webview's `PreferredColorScheme` (tauri-runtime-wry). That answers the question the Theme box asked, whether `set_theme` also sets WebView2's preferred color scheme: yes, and since that setting belongs to the WebView2 profile every window shares, a theme always applies to every window (the evidence is in ticket 13's [cause and fix](13-white-backdrop-behind-a-dark-page.md)). So the theme can be one call for the whole app, and only the backdrop is per window. **Open, for the repo owner:** a per-window `Windows::set_look` (recommended: one shape for both, the recorder sees it, and the adapter may call `AppHandle::set_theme` inside it), or a separate theme call for the whole app.
- **Broken values.** The cost list per setting (ticket 06's comment above) left out "a broken value loads the default", one of this ticket's boxes; today one bad field sends the whole settings file to `.bad`. Proposed: one generic serde helper on every field of `Settings`, the existing ones too, that gives the field its default when its value doesn't parse. The cost list now has that line.
- **`backdrop.ts` has no page test today.** The test named in ticket 12's closing pass above (a `settings` message with Backdrop None brings back the solid background) covers it, and it is now in the page tests' box.
