# 04: Text dropped onto a window shows as a paste

**What to build:** The reader drags text from another program (a browser, an editor, a chat) onto a Downlight window, and the window shows it rendered, as **Paste** shows the clipboard's text: Downlight writes it to `Dropped <time>.md` in the pasted folder, the window shows that file, it joins **History**, and it is deleted as a paste is. A drag that carries files still opens its file. A drag that started in the same window, or has no text but whitespace, gets the no-drop cursor. A drop is always a copy, so the program the text came from keeps it.

Spec: [Paste Markdown](../spec.md) (Text drops), [ADR 0006](../../../docs/adr/0006-a-paste-is-a-file-downlight-writes.md), [ADR 0007](../../../docs/adr/0007-downlight-takes-drops-with-its-own-drop-target.md)

## Results

Built on 2026-11-25.

- **The tag reaches the drop target, in one Chromium format (decided from Chromium's source; the hand check must confirm it).** Chromium doesn't put a custom `dataTransfer` type into the OLE data object as a clipboard format of its own name. It writes every custom type of a drag into one registered format, `Chromium Web Custom MIME Data Format` (`ClipboardFormatType::DataTransferCustomType()` in `ui/base/clipboard/clipboard_format_type_win.cc`), as a `base::Pickle` of the types and their data: `PrepareDragData` in `content/browser/web_contents/web_contents_view_aura.cc` calls `WriteCustomDataToPickle(drop_data.custom_data)` and `SetPickledData` whenever the page set any, with no condition on where the drag goes, and `OSExchangeDataProviderWin::SetPickledData` copies the whole pickle into a `TYMED_HGLOBAL` medium. The pickle is a 4-byte header with the payload's size, then a `uint32` count and each type and its data as a `String16` (an `int32` length in UTF-16 units, the units, padded to 4 bytes; `custom_data_helper.cc`, `base/pickle.cc`). Chromium reads its own drags back the same way, and drags of custom types between two Chrome instances are reported to work, so the drop target registers the same name (which answers the same format in every process) and reads the tag from it. The alternative, the page telling the app when its drags start and end, was set aside: the message and OLE's DragEnter both reach the main thread with no order between them, and a `dragend` that never comes would leave every later drag refused.
- **Reading it.** `started_in` in `app/src/platform/windows/drop_target.rs`: safe Rust over the locked medium's bytes, never past `GlobalSize` or the header's payload size, with checked lengths; anything that doesn't read as Chromium writes it, no format, no medium or no tag means "not from this window", never a refusal or a crash. The type is `application/x-downlight-window` (lowercase, as Blink lowercases a type) and its data the window's label.
- **The drop target.** At DragEnter it reads the drag once (`Drag::onto`), unless its source allows no copy: a drag tagged with this window is refused first; then paths as before (a drag with any is a file drop); then `CF_UNICODETEXT`, up to the first NUL and never past `GlobalSize`. Whitespace is checked on the medium without copying it again (`char::is_whitespace`, as Paste's `str::trim`). A drag it takes is kept in the target until DragLeave or Drop: `GetData`'s medium is the caller's until `ReleaseStgMedium`, so Drop copies the text out of the kept medium (`String::from_utf16_lossy`) instead of having the source copy all of it across processes a second time. DragEnter, DragOver and Drop each answer `DROPEFFECT_COPY` only when the drag is taken and the source allows a copy (`*pdwEffect` on entry, as OLE's contract asks), else `DROPEFFECT_NONE`, never a move; Drop hands the drag on only when it answers a copy. The clipboard's text and the drag's medium are locked through one guard, `LockedGlobal` in `app/src/platform/windows/global_memory.rs` (windows-sys's `GlobalLock`). The `windows` crate gained `Win32_System_DataExchange`; Cargo.lock and the notices are unchanged.
- **The interface.** `platform::add_drop_target(&window, dropped: impl Fn(open::Dropped) + Send + 'static)`, with `open::Dropped::{Files(Vec<PathBuf>), Text(String)}`; it takes the window's label from the window itself. Other systems' do-nothing version takes the same callback. `open::take_drops` hands every drop to `show_dropped_off_the_main_thread`, shared with `show_when_dropped`: one blocking task per drop, which shows the files as before or has the paste module show the text.
- **The paste module.** A private `Came { Pasted, Dropped }` names the file (`Pasted ...` or `Dropped ...`); `paste` (the clipboard) is unchanged outside, and `paste::show_dropped_text(documents, window, text, at)` is the drop's: Paste's refusals and Notices, sent to the window as a file drop's are, except that text with nothing to show says nothing (the drop target refused its drag already). The drop's blocking task in `open.rs` reports `timing <window> drop at=... show=...` with the timing switch.
- **The tag's type is a contract sample.** `open::DRAG_TAG` is sampled to `app/tests/fixtures/drag_tag.json`, and the page's test of its tag (`drags.test.ts`) reads the type from there, so the page's `DRAG_TAG` in `app.ts` and the app's can't drift apart.
- **Page.** `page/src/drags.ts` tags every `dragstart` in the page (captured on the document, so an element that stops the event can't keep a drag untagged) with `windowLabel()` from `app.ts`. The empty window's hint names dropping text.
- **Tests.** Seven in `app/src/documents/tests/paste.rs` (a new `Dropped ...` file holding the text as UTF-8, two in the same second, Back, a document on its way, whitespace and empty text changing nothing and saying nothing, a failed write naming the file, deleted when its window closes), two in `drags.test.ts`, and `view.test.ts`'s hint. The drop target itself is checked by hand (Testing Decisions).
- **The pickle reader now has unit tests.** `drop_target.rs`'s tests write pickles as `WriteCustomDataToPickle` does and check `custom_data` and the tag (found among other types past padding, absent, another window's label, an empty or short buffer, a payload size past the end, a negative length, a length of `0x7FFF_FFFF`, a last string without its padding, which reads as Chromium's `AlignAfterRead` lets it, and a count larger than the strings present) and `shows_something` against Paste's `str::trim` (whitespace with U+3000, visible text, a lone surrogate).
- **Measuring (left for the owner).** Run `npm run documents`, open `target/documents/mixed-1mb.md` in Notepad, run the release build with `DOWNLIGHT_TIMING` set, select all in Notepad and drag it onto a window 5 times, and take the medians of the `timing <window> drop ... show=...` lines (writing the file and giving it to the window); the render is reported after it as any document's is. Copying the text out on the main thread at Drop isn't in the line; a 20 MB drop's hand check shows whether it is felt.
- **Left.** The measurement and the hand checks, among them the tag: a selection, a link and an image dragged inside the window and dropped there must do nothing, and a selection from another Downlight window must show.
