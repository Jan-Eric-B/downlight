# 03: Find's marks, and clicking them

**What to build:** While the find bar has matches, the **Overview ruler** marks each match of **Find** and, apart from them, the **Current match**, so the reader sees where the matches cluster. A click on a Find mark makes the match nearest the pointer the current match and scrolls it into view, as F3 does.

Spec: [Overview ruler](../spec.md)

**Blocked by:** 01 (Heading marks beside the scroll bar)

**Status:** ready-for-agent

- [x] Find gains a listener for when its matches or its current match change (a recount as the reader types, a step with Enter, F3 or the arrow buttons, a reload's recount, the bar closing), and a way to make a given match current and scroll it into view as a step does. `findMatches()` stays the read side; Find keeps owning the current match.
- [x] A match's mark sits at its top-level block's top plus its share of that block's text times the block's height; no rectangle inside the block is read.
- [x] Match marks are short marks in the strip's right half in the accent's Find match role; the current match is the full width, a little thicker, in the current match role. A heading mark and a match mark in one row both show.
- [x] The marks appear as the reader types, follow each step, and go when Find closes.
- [x] A click in the strip's right half near a match mark makes the nearest match current and scrolls to it, without joining **History**.
- [x] The accent test that lists every use of the accent roles in the stylesheets gains the ruler's two uses.
- [x] Page tests (written first): marks appear for the typed text and follow Enter and F3; closing Find removes them; a click on a match mark makes the nearest match current and Back doesn't return from it.
- [ ] Hand check in the release build: the colors with Amber and with Windows' accent, in light and dark, and in a high contrast theme (the system's highlight colors).
- [x] `npm run check` passes (its Prettier step fails only on a stray worktree under `.claude/worktrees/`, not this repo's files; every other step passes when run on its own).

## Decisions

- **Find's interface** (`find.ts`) grows by two functions and a type, beside `findMatches()`, which now returns `FoundMatches` (`matches`, `current`): `whenMatchesChange(listener)` hears the matches and the current match each time either changes (a count as the reader types, a reload's or another document's count, a step, `goToMatch`, the bar closing), and `goToMatch(index)` makes the match at that index of `findMatches()` current and goes to it exactly as a step does (the step itself now goes through it), so it never joins History; an index Find has no match at does nothing. `matches` is the same array until Find counts again, so a reader tells a step, which only moves the current match, from a count by the array. Find doesn't tell its listeners of a count that finds nothing after one that found nothing, and keeps its empty array then, so typing on in a box with no results costs the ruler nothing. Find tells its listeners of a step after the step's scroll has started, so a listener that throws can't keep the view from the match. Later Find features (options, Sort's reorder) keep the ruler working as long as they count through `show` and step through `goTo`.
- **A match's place in its block** is the share of the block's text before the match's start, from one walk through the block's text nodes for all of its matches, in document order, which sums the text nodes' lengths (`CharacterData.length`) as it goes, so a count builds no string of a block's text. Text in a closed section counts in its block's share, though the closed section shows only its summary; Find opens the section when it goes to a match. A cache of each block's text offsets for the render, kept from count to count, is left to ticket 05, if a larger document needs it.
- **What redraws, by cause.** A count, a size change, the headings, the document, the switch or the wait note redraw the whole strip: a count places the matches in their blocks again, and every redraw measures the blocks and rebuilds the marks. A step (Enter, F3, the arrow buttons, a click on a mark) keeps the matches' array, so it only moves the current match's mark, which is kept from draw to draw: one style write, nothing read.
- **Rows.** Each redraw sorts the matches into the strip's pixel rows once (a counting sort), so a click looks only at the rows within `MARK_REACH` of it rather than at every match, and the marks are drawn from the rows: one element for each run of rows whose marks touch (a match's mark covers its row and the next), which looks the same as one mark per row.
- **Mark sizes:** a match's mark 7 px long (the strip's right half), 2 px high (`MATCH_MARK_HEIGHT` in the script, which sets each run's height), at the strip's right edge; the current match's 14 px and 3 px high, drawn after the match marks so it lies over them. Every match has a mark in Find's lane, the current one too, under the current match's mark. The current match's mark, the full width, covers a heading mark in the same row: the spec's full width, accepted, since it is one row and Find's current match is what the reader is looking for then. Under forced colors they take `forced-color-adjust: none` and keep the Find roles, which `accent.css` sets to `Mark` and `Highlight` there, as Find's highlights do.
- **Clicks with a strip that takes no pointer.** The strip keeps `pointer-events: none` (ticket 01), so the wheel over it still scrolls the document. The ruler hears `mousedown` and `click` on the scroller, which the content under the strip gets, and places them by the scroller's box (its top and right, less the scroll bar), read at the click; the strip's width is `STRIP_WIDTH` in the script, which sets `--overview-ruler-width` on the strip for the stylesheet, so the width has one source. A click acts only when its press was on a mark too: the press arms it, and only a left press on a mark does, which is then prevented, so the focus stays where it is, in the find box too, and no selection starts. The webview gives a click whose press was elsewhere to the element that holds both, so a selection dragged from the text and let go beside a mark would otherwise reach the scroller as a click on the mark. A press or click acts only when it lands on the scroller or the document view (not the "File deleted or moved" bar or the wait note, which lie over the strip), with the left button, unprevented by anything in the document, in the strip's right half, and within 4 px of a match's place (`MARK_REACH`; marks are 2 and 3 px high); the click then picks the match nearest the pointer, the first of equals. A click near no mark, or while Find has no matches, is left alone as if the strip weren't there (in the margin or the document's right padding, so it does nothing). A click between a count and the strip's redraw of it (one frame) does nothing, since the marks it was aimed at are of the last count.
- **The strip's left half is ticket 04's.** A click in it does nothing here, even beside the current match's full-width mark; ticket 04 decides whether a left-half click with no heading mark near falls back to a match.
- **The pointer** stays the arrow over Find's marks for now: the hand over a mark is ticket 04's, which has to set it on the scroller, since the strip takes no pointer.
- **No contract shape changed**, so no fixtures were written.

- **Each keystroke's count shows as soon as without the ruler**, within the spread between runs: 15.8 against 14.8 ms in the median, the slowest later keystroke 39.6 against 38.3 ms.
- **The frame over 100 ms on 1 MB mixed is Find's, not the ruler's.** A third session ran the same build with temporary probes (the ruler's redraws, timed, and every animation frame over 60 ms with its scripts, from the Long Animation Frames API), on 1 MB mixed only. The probes are removed again. In each of the 5 runs, the long frame is the frame of Find's count for "e" (105,831 matches): one timer task of 60 to 80 ms (Find's last index slice and its count) and 26 to 28 ms of render, 88 to 108 ms in all, and it ends before the ruler does anything with the matches. The ruler's redraw for those matches comes in the next frame: a task of 25 to 30 ms (22 to 26 ms of it measuring the blocks and placing the matches), and a frame of 62 to 66 ms with its render. The counts after it redraw in 8 to 23 ms (49,487 matches for "t", 47,346 for "the", 7,367 for "th"). That session's median was 105.0 ms (worst 107.9), with 2 of the 5 runs at 0.
- So the ruler doesn't make the longest frame longer: the 0 without the ruler is a session in which Find's frame stayed under 100 ms, as in ticket 01's diagnosis (80 to 125 ms with or without the ruler, depending on garbage collection). Getting Find's frame under 100 ms is still v1 ticket 40's. The ruler's own frame after a one-letter count, about 65 ms, is the one to watch in ticket 05 (in slices or on a canvas there, if a larger document takes it over 100 ms).
- **The rest of the measurement (first session)**, ruler on: scrolling through both 1 MB documents gave no task or frame over 100 ms (worst 0); the frame after the document goes in (`longestAfterDocument`) 0 for 100 KB, 1 MB mixed and 1 MB prose; first paint 797.5, 1151.7 and 833.9 ms, in line with ticket 01's session (the core's read and render set it, 534 and 831 ms for 100 KB and 1 MB mixed).

- **Holding F3 costs the ruler nothing**: no task or frame over 100 ms in either ruler-on session, and each step done in two frames (33.5 and 41.5 ms). The steps were faster with the ruler on than off in both pairs of sessions (about 35 against 68 ms), which the ruler's own work can't explain, since with it off it does nothing; a likely cause, not probed, is that the ruler's redraw after the count reads every block with a match, which leaves the document's layout up to date for the steps' scrolls. The off session's worst run (145 ms, 209 ms for one step) is that run's alone.
- **Each keystroke's count shows as soon as without the ruler** (15.1 to 17.1 ms in the median either way).
- **The longest frame while typing is longer with the ruler on**: 138.0 and 171.9 ms in the median, every one of the ten runs over 100 ms (120 to 193), against 109.6 and 0.0 with it off (0 to 126). The machine was slower today than in the first session (first paint of 1 MB mixed 1,079 to 2,201 ms across sessions, against 1,151.7), and Find's own frame for "e" crossed 100 ms in most ruler-off runs, against none in the first session, so part of the rise is the machine; the 30 to 60 ms the ruler adds above it is more than the first session's probes found (the ruler's frame after the count apart from Find's, 62 to 66 ms). Nothing these fixes changed adds work to a count (placement builds no strings now, and the rows are one counting sort), so it is open whether the ruler's frame now lands in Find's, or is only the machine's: a probe session, as above, with the Long Animation Frames API, would tell. That frame stays ticket 05's to watch (and v1 ticket 40's for Find's part).
- 1 MB prose, the rest of the cases, ruler on again: typing 13.6 ms per keystroke, no long frame (worst 0.0); scrolling through both 1 MB documents no task or frame over 100 ms (worst 0); a reload in the middle of 1 MB mixed kept the reading position (0 lines moved).
